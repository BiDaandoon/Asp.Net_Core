    How Git and GitHub Work Together

    چگونه گیت و گیت‌هاب با هم کار می‌کنند¶

    قبل از یادگیری عملیات GitHub، یک ایده ساده را کاملاً واضح در نظر داشته باشید: Git و GitHub با هم مرتبط هستند، اما یکسان نیستند. Git یک سیستم کنترل نسخه است که تغییرات کد را ردیابی می‌کند، تاریخچه را حفظ می‌کند، شاخه‌ها را مدیریت می‌کند و به ما امکان می‌دهد تغییرات کد را به روشی ساختاریافته commit، merge، push و pull کنیم. GitHub یک پلتفرم میزبانی آنلاین است که مخازن Git را در اینترنت ذخیره می‌کند تا بتوان آنها را به اشتراک گذاشت، از آنها نسخه پشتیبان تهیه کرد، بررسی کرد و بین چندین توسعه‌دهنده همگام‌سازی کرد.

    در توسعه روزمره:

    • ما کد را روی رایانه خودمان درون یک مخزن محلی می‌نویسیم
    • ما با استفاده از گیت، کامیت‌ها را به صورت محلی ایجاد می‌کنیم
    • وقتی می‌خواهیم آن کار را به اشتراک بگذاریم، ارسال می‌کنیم آن کامیت‌ها را به گیت‌هاب
    • وقتی شخص دیگری کار جدیدی را به گیت‌هاب ارسال می‌کند، ما منتقل می‌کنیم . آن تغییرات را به دستگاه محلی خود

    این پایه و اساس همکاری واقعی است.

    به زبان ساده:

    • گیت : موتور کنترل نسخه واقعی. این موتور روی دستگاه شما اجرا می‌شود و عملیات افزودن، کامیت، شاخه‌بندی، ادغام، کشیدن و ارسال را انجام می‌دهد.
    • گیت‌هاب : پلتفرم آنلاینی که مخازن گیت شما را میزبانی می‌کند و آنها را از طریق اینترنت در دسترس قرار می‌دهد.
    • مخزن محلی : مخزنی روی رایانه شما که کارهای توسعه واقعی را در آن انجام می‌دهید.

    را درون سرویس‌ها اضافه کنید فایل ProductService.cs .

    using ProductCatalog.API.Models;

namespace ProductCatalog.API.Services
{
    public class ProductService : IProductService
    {
        private static readonly List<Product> _products = new()
        {
            new Product { Id = 1, Name = "Keyboard", Price = 1500 },
            new Product { Id = 2, Name = "Mouse", Price = 800 }
        };

        public List<Product> GetAll()
        {
            return _products;
        }

        public Product? GetById(int id)
        {
            return _products.FirstOrDefault(p => p.Id == id);
        }

        public Product Add(Product product)
        {
            // محاسبه Id جدید با در نظر گرفتن خالی بودن لیست
            var nextId = _products.Any() ? _products.Max(p => p.Id) + 1 : 1;
            product.Id = nextId;
            _products.Add(product);
            return product;
        }
    }
}

    using ProductCatalog.API.Services;

namespace ProductCatalog.API
{

    {
        public static void Main(string[] args)

            // Add services to the container.
            builder.Services.AddControllers();
            builder.Services.AddEndpointsApiExplorer();
            builder.Services.AddSwaggerGen();

                app.UseSwagger();
                app.UseSwaggerUI();

            app.UseHttpsRedirection();

            app.UseAuthorization();

            app.MapControllers();

            app.Run();
        }
    }
}
    ایجاد ProductsController.cs¶

    داخل پوشه Controllers ، فایل ProductsController.cs را اضافه کنید .

    using Microsoft.AspNetCore.Mvc;
using ProductCatalog.API.Models;
using ProductCatalog.API.Services;

namespace ProductCatalog.API.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class ProductsController : ControllerBase
    {
        private readonly IProductService _productService;

        public ProductsController(IProductService productService)
        {
            _productService = productService;
        }

        [HttpGet]
        public IActionResult GetAll()
        {
            return Ok(_productService.GetAll());
        }

        [HttpGet("{id:int}")]
        public IActionResult GetById(int id)
        {
            var product = _productService.GetById(id);

            if (product == null)
                return NotFound($"Product with Id {id} not found.");

            return Ok(product);
        }

        [HttpPost]
        public IActionResult Add(Product product)
        {
            var created = _productService.Add(product);
            return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
        }
    }
}

    درخواست‌های Pull (PR) در گیت‌هاب¶

    درخواست Pull یک درخواست رسمی برای ادغام تغییرات از یک شاخه به شاخه دیگر است، که معمولاً از یک شاخه ویژگی یا شاخه رفع اشکال به شاخه اصلی است. این فقط یک دکمه ادغام نیست. این یک گردش کار قابل بررسی است که به تیم اجازه می‌دهد تغییرات را قبل از تبدیل شدن به بخشی از پایگاه کد پایدار، بررسی کند. به جای ادغام بی‌سروصدای کد در شاخه اصلی، درخواست Pull کل تغییر را برای سایر توسعه‌دهندگان قابل مشاهده می‌کند. آنها می‌توانند فایل‌های تغییر یافته را بخوانند، منطق را مورد بحث قرار دهند، درخواست بهبود دهند، آنها را تأیید کنند و سپس آنها را به روشی کنترل‌شده ادغام کنند.

    تیم‌ها از درخواست‌های Pull استفاده می‌کنند زیرا قبل از رسیدن کد به شاخه اصلی، یک Checkpoint با کیفیت اضافه می‌کنند. بدون آن Checkpoint، یک توسعه‌دهنده می‌تواند کد ناقص، پرخطر یا نادرست را مستقیماً به شاخه پایدار ارسال کند. این می‌تواند کل تیم را تحت تأثیر قرار دهد. ممکن است ساخت برنامه متوقف شود، APIها ممکن است نادرست رفتار کنند یا اشکالات پنهان وارد مرحله تولید شوند. PRها با دادن فرصتی به تیم برای بررسی کد قبل از ادغام، این ریسک را کاهش می‌دهند.

    شاخه اصلی همیشه باید نمایانگر کد پایدار و قابل اعتماد باشد. کارهای جدید، مانند اضافه کردن ویژگی‌ها، رفع اشکالات و آزمایش‌ها، باید در شاخه‌های جداگانه انجام شوند. شاخه‌بندی به شما امکان می‌دهد تا ضمن حفظ ثبات شاخه اصلی، به طور مستقل توسعه دهید.

    چرا شاخه‌بندی اهمیت دارد؟¶
    • شما می‌توانید بدون ایجاد اختلال در کد پایدار، یک ویژگی ایجاد کنید
    • می‌توانید با خیال راحت یک اشکال را برطرف کنید و قبل از ادغام، آن را آزمایش کنید
    • چندین توسعه‌دهنده می‌توانند به صورت موازی کار کنند
    • کار نیمه تمام تا زمان آماده شدن، ایزوله می‌ماند.
    قرارداد نامگذاری توصیه‌شده¶
    • feature/add-teacher-api
    • feature/add-authentication
    • bugfix/fix-student-validation
    • bugfix/fix-login-null-ref
    • hotfix/fix-payment-error-in-production
    شاخه را کجا باید ایجاد کنیم؟¶

    یک شاخه (branch) یک ویژگی گیت است ، نه یک ویژگی مختص گیت‌هاب. این بدان معناست که شاخه‌ها معمولاً با استفاده از گیت در مخزن محلی شما ایجاد می‌شوند و سپس به گیت‌هاب ارسال می‌شوند تا گیت‌هاب بتواند آنها را ذخیره و نمایش دهد. در توسعه واقعی، جریان شاخه‌بندی عادی همیشه ابتدا محلی است.

    بنابراین، گردش کار به شرح زیر است:

    • ایجاد یک شاخه به صورت محلی
    • به آن شاخه تغییر دهید
    • کارهای توسعه‌ای خود را انجام دهید
    • به صورت محلی کامیت کنید
    • ارسال شاخه به گیت‌هاب
    • سپس گیت‌هاب همان شاخه را به صورت آنلاین نشان می‌دهد

    آزمایشگاه ۱: ایجاد یک شاخه ویژگی، باز کردن یک درخواست pull، درخواست تغییرات، رفع آن، تأیید آن، ادغام آن¶

    بخش اول: باز کردن پروژه موجود در ویژوال استودیو¶
    1. را باز کنید ویژوال استودیو
    2. راهکار موجود خود را باز کنید: ProductCatalog.API
    3. به گوشه پایین سمت راست نگاه کنید
    4. نام شاخه فعلی را تأیید کنید
    5. در حالت ایده‌آل باید نشان دهد: صفحه اصلی

    اگر شاخه اصلی نیست، روی نام شاخه کلیک کنید و به شاخه اصلی بروید.

    بخش ۲: آخرین شاخه اصلی را بکشید¶

    در ویژوال استودیو:

    1. به منوی بالا بروید
    2. کلیک کنید روی گیت
    3. کلیک کنید بکشید

    این دستور، شاخه اصلی محلی شما را از گیت‌هاب به‌روزرسانی می‌کند. این کار را قبل از ایجاد شاخه PR جدید انجام دهید.

    بخش ۳: ایجاد شاخه ویژگی‌ها در ویژوال استودیو¶

    حالا، بیایید با استفاده از یک شاخه ویژگی، یک API جدید اضافه کنیم. می‌خواهیم یک API دسته‌بندی جدید بدون دست زدن مستقیم به شاخه اصلی پایدار اضافه کنیم. ما یک شاخه ویژگی از شاخه اصلی ایجاد خواهیم کرد تا کار جدید ایزوله بماند و کد پایدار را مختل نکند.

    گام به گام در ویژوال استودیو¶
    1. مطمئن شوید که در مسیر اصلی هستید
    2. آخرین تغییرات را برای صفحه اصلی دریافت کنید
    3. را باز کنید مخزن گیت یا مدیریت شاخه‌ها بروید. یا به View → Git Repository
    4. روی فایل اصلی کلیک راست کنید و گزینه New Local Branch From… یا New Branch را انتخاب کنید.
    5. یک نام شاخه معنادار وارد کنید: feature/add-category-api
    6. بررسی کنید شعبه پرداخت را
    7. کلیک کنید روی ایجاد

    حالا در پایین سمت راست تأیید کنید که ویژوال استودیو عبارت feature/add-category-api را نشان می‌دهد . این یعنی حالا تمام تغییرات شما به این شاخه منتقل می‌شوند، نه به شاخه اصلی.

    بررسی کد چیست؟¶

    بررسی کد فرآیندی است که در آن سایر توسعه‌دهندگان تغییرات کد شما را قبل از ادغام بررسی می‌کنند. این معمولاً در داخل درخواست Pull اتفاق می‌افتد.

    در طول بررسی کد، بررسی‌کنندگان موارد زیر را بررسی می‌کنند:

    • اینکه منطق درست است یا نه
    • اینکه آیا کد قابل خواندن است یا خیر
    • اینکه آیا نامگذاری واضح است یا خیر
    • چه باگ یا ریسکی وجود داشته باشد
    • آیا استانداردهای کدنویسی رعایت می‌شوند؟
    • اینکه آیا تغییر باید قبل از ادغام بهبود یابد یا خیر

    بنابراین، بررسی کد به این معنی است که سایر توسعه‌دهندگان قبل از ادغام، تغییرات شما را می‌خوانند و ارزیابی می‌کنند. فرض کنید یک PR برای feature/add-category-api باز کرده‌اید. یک بررسی‌کننده ممکن است موارد زیر را بررسی کند:

    • آیا CategoriesController به درستی نامگذاری شده است؟
    • آیا مسیر درست است؟
    • آیا ساختار پاسخ واضح است؟
    • آیا کد ساده و خوانا است؟
    • آیا برای ایجاد ثبات، باید بعداً یک لایه سرویس اضافه شود؟
    چگونه داوران بازخورد می‌دهند؟¶

    داوران معمولاً مستقیماً در داخل درخواست Pull در GitHub بازخورد می‌دهند. آن‌ها می‌توانند فایل‌های تغییر یافته را خط به خط بررسی کنند و در مورد خطوط خاص کد نظر بگذارند، یا می‌توانند بازخورد کلی در مورد کل PR ارائه دهند.

    بازخوردهای معمول ممکن است شامل موارد زیر باشد:

    • درخواست نامگذاری بهتر
    • پیشنهاد بازسازی
    • به اعتبارسنجی از دست رفته اشاره کنید
    • ریسک‌های منطقی را برجسته کنید
    • ساده‌سازی را توصیه کنید
    • یک رویکرد پاک را ستایش کنید
    بخش ۱۰: بررسی عملی PR در گیت‌هاب¶

    حالا، بیایید یک بررسی واقعی را شبیه‌سازی کنیم.

    مراحل

    1. درخواست Pull را باز کنید
    2. کلیک کنید « فایل‌های تغییر یافته» روی برگه
    3. باز کردن Category.cs
    4. موس را روی خط زیر نگه دارید: public string Title { get; set; } = string.Empty;
    5. روی آیکون آبی + کنار خط کلیک کنید
    6. این نظر را اضافه کنید: لطفاً عنوان را به نام تغییر دهید تا با نام محصول در پروژه ما سازگار بماند و روی نظر کلیک کنید.
    7. اگر می‌خواهید، یک نظر دیگر در CategoriesController.cs اضافه کنید: کنترلر تمیز به نظر می‌رسد. بعداً می‌توانیم داده‌های نمونه را برای سازگاری بهتر به یک سرویس منتقل کنیم و روی نظر کلیک کنیم.

    3. کد به‌روزرسانی‌شده را تأیید کنید
    4. کلیک کنید روی مرور تغییرات
    5. در کادر نظر، عبارت زیر را تایپ کنید: تغییر نام درخواستی اعمال شد. اکنون خوب به نظر می‌رسد.
    6. انتخاب: تایید
    7. کلیک کنید روی ارسال نظر

    حالا PR تایید شده است. اینگونه است که Approve عملاً کار می‌کند.

    بخش ۱۴: قبل از ادغام بررسی کنید¶

    قبل از ادغام یک درخواست Pull، تیم باید تأیید کند که کد واقعاً آماده است.

    چک لیست قبل از ادغام

    • آیا پروژه با موفقیت ساخته شد؟
    • آیا آزمون‌ها با موفقیت پشت سر گذاشته شده‌اند؟
    • آیا به نظرات داوران رسیدگی شده است؟
    • آیا شعبه از نظر اطلاعات اصلی به‌روز است؟
    • آیا تداخلات ادغام حل شده است؟
    • آیا کد از نظر منطقی درست است؟
    • آیا استانداردهای نامگذاری و کدگذاری قابل قبول هستند؟
    • آیا توضیحات روابط عمومی به اندازه کافی واضح است؟
    • آیا اطلاعات محرمانه یا حساسی به طور تصادفی در آن گنجانده شده است؟
    • آیا ویژگی یا اصلاحیه برای نسخه اصلی به اندازه کافی کامل است؟

    برای مثال ما، موارد زیر را تأیید کنید:

    • Category.cs درست است
    • CategoriesController.cs درست است
    • تست سواگر جواب داد
    • نظر منتقد اصلاح شد
    • روابط عمومی تایید شده است
    بخش ۱۵: ادغام درخواست Pull در گیت‌هاب¶

    حالا روابط عمومی را ادغام کنید.

    مراحل¶
    1. درخواست Pull تایید شده را باز کنید
    2. کلیک: درخواست ادغام
    3. سپس کلیک کنید: ادغام را تأیید کنید
    4. اکنون تغییرات شاخه در شاخه اصلی ادغام شده‌اند:
    5. پس از ادغام، گیت‌هاب ممکن است عبارت زیر را نمایش دهد: حذف شاخه. اگر شاخه ویژگی دیگر مورد نیاز نیست، روی آن کلیک کنید.

    اکنون فایل اصلی شامل موارد زیر است:

    • دسته‌بندی.cs
    • دسته بندی هاController.cs

    این اتفاقی است که عملاً بعد از ادغام PR می‌افتد.

    بخش ۱۶: به‌روزرسانی فایل اصلی محلی در ویژوال استودیو پس از ادغام¶

    ادغام در گیت‌هاب نمی‌کند . به طور خودکار پروژه ویژوال استودیو محلی شما را به‌روزرسانی

    شما باید فایل اصلی محلی را به‌روزرسانی کنید.

    مراحل¶
    1. بازگشت به ویژوال استودیو
    2. شاخه را به شاخه اصلی تغییر دهید
    3. بروید به گیت
    4. کلیک کنید بکشید

    اکنون، فایل اصلی محلی، کد ادغام‌شده را از گیت‌هاب دریافت می‌کند.

    اختیاری: حذف شاخه محلی

    اگر انجام شود:

    1. نمای باز → مخزن گیت
    2. کلیک راست: feature/add-category-api
    3. کلیک کنید روی حذف

    اکنون پروژه محلی شما کاملاً با PR ادغام‌شده همگام‌سازی شده است.

    آزمایشگاه ۲: ایجاد و ادغام یک درخواست pull برای رفع اشکال¶

    حالا، بیایید یک PR واقعی دیگر انجام دهیم، اما این بار برای رفع اشکال. می‌خواهیم اعتبارسنجی را در اکشن POST از ProductsController اضافه کنیم. این کار گردش کار را حتی واضح‌تر می‌کند.

    بخش ۱۷: ایجاد شاخه رفع اشکال (Bug-Fix Branch) در ویژوال استودیو¶

    مراحل

    1. به صفحه اصلی تغییر دهید
    2. آخرین نسخه اصلی را بکشید
    3. باز کنید مخزن گیت را
    4. کلیک راست روی صفحه اصلی
    5. کلیک کنید روی شاخه جدید
    6. از این نام استفاده کنید: bugfix/fix-product-validation
    7. بررسی کنید شعبه پرداخت را
    8. کلیک کنید روی ایجاد

    حالا شما در شاخه رفع اشکال هستید.

    بخش ۱۸: افزودن اعتبارسنجی در ProductsController¶

    فایل ProductsController.cs را باز کنید و اکشن POST را به‌روزرسانی کنید. متد Add را با این کد جایگزین کنید:

    [HttpPost]
public IActionResult Add(Product product)
{
    if (string.IsNullOrWhiteSpace(product.Name))
    {
        return BadRequest("Product name is required.");
    }

    if (product.Price <= 0)
    {
        return BadRequest("Product price must be greater than zero.");
    }

    var created = _productService.Add(product);
    return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
}
    آن را آزمایش کنید¶

    Swagger را اجرا کنید و تست کنید:

    • پست با نام خالی
    • پست با قیمت ۰
    • ارسال با داده‌های معتبر

    مطمئن شوید که اعتبارسنجی به درستی کار می‌کند.

    بخش ۱۹: کامیت کردن و ارسال شاخه رفع اشکال (Bug-Fix Branch)¶
    1. پیام کامیت: اعتبارسنجی را به اکشن POST محصول اضافه کنید
    2. به گیت → پوش بروید

    حالا این شاخه روی گیت‌هاب است.

    بخش ۲۱: بررسی، تأیید و ادغام PR رفع اشکال¶

    حالا دقیقاً همان چرخه روابط عمومی را تکرار کنید:

    1. داور روابط عمومی را باز می‌کند
    2. بررسی تغییر فایل‌ها
    3. در صورت لزوم، نظراتی را اضافه می‌کند
    4. کلیک‌ها تأیید می‌شوند
    5. ادغام روابط عمومی
    6. در صورت اتمام، شاخه را حذف کنید

    سپس در ویژوال استودیو:

    1. به صفحه اصلی تغییر دهید
    2. کلیک کنید بکشید

    اکنون فایل اصلی محلی شما شامل هر دو مورد زیر است:

    • ویژگی دسته بندی ها
    • رفع اشکال اعتبارسنجی محصول

    تداخل ادغام چیست؟¶

    تداخل ادغام زمانی اتفاق می‌افتد که گیت نمی‌تواند به‌طور خودکار تصمیم بگیرد که چگونه تغییرات دو شاخه را با هم ترکیب کند. این معمولاً زمانی اتفاق می‌افتد که هر دو شاخه، یک فایل و خطوط مشابه یا خطوط نزدیک به هم را به روش‌های مختلف تغییر می‌دهند. گیت نمی‌گوید که پروژه شما خراب است. بلکه صرفاً از شما می‌خواهد که تصمیم بگیرید.

    حوزه‌های تداخل رایج در پروژه‌های ASP.NET Core¶
    • Program.cs زمانی که چندین توسعه‌دهنده سرویس‌ها یا میان‌افزار اضافه می‌کنند
    • کنترلرها وقتی که متد اکشن یکسان به طور متفاوتی تغییر داده می‌شود
    • DTOها یا مدل‌ها وقتی چندین شاخه، ویژگی‌ها را اضافه یا تغییر نام می‌دهند
    • appsettings.json وقتی تغییرات پیکربندی با هم همپوشانی دارند
    • ثبت تزریق وابستگی زمانی که چندین ویژگی، سرویس‌ها را به‌روزرسانی می‌کنند

    شبیه‌سازی یک تداخل ادغام واقعی در Program.cs¶

    حالا، بیایید یک تضاد عملی ایجاد کنیم.

    تغییر در شاخه اصلی¶

    فرض کنید، در اصل، شما Program.cs را طوری تغییر می‌دهید که نامگذاری camelCase JSON را غیرفعال کند.

    builder.Services.AddControllers()
    .AddJsonOptions(options =>
    {
        options.JsonSerializerOptions.PropertyNamingPolicy = null;
    });

    این را در main با پیام زیر commit کنید: پیکربندی سریال‌سازی JSON برای حفظ نام‌های ویژگی C#

    تغییر در شاخه رفع اشکال¶

    حالا به bugfix/fix-product-validation بروید و Program.cs را به طور متفاوتی تغییر دهید تا یک سیاست CORS اضافه شود.

    builder.Services.AddControllers();

builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowAll", policy =>
    {
        policy.AllowAnyOrigin()
              .AllowAnyMethod()
              .AllowAnyHeader();
    });
});

    همچنین اضافه کنید:

    app.UseCors("AllowAll");

    این شاخه را با این پیام ثبت کنید: سیاست CORS را اضافه کنید تا به همه ریشه‌ها اجازه داده شود. اکنون، هر دو شاخه Program.cs را در قسمت‌های همپوشانی تغییر داده‌اند. این یک تضاد واقعی ایجاد می‌کند.

    نکته: تداخل ادغام زمانی رخ می‌دهد که دو شاخه یک فایل را تغییر می‌دهند و گیت نمی‌تواند به طور خودکار کد نهایی را تعیین کند. تداخل، شکست گیت نیست. بلکه یک نقطه تصمیم‌گیری است. کد را بخوانید، الزامات تجاری را درک کنید و نتیجه ترکیبی نهایی صحیح را ایجاد کنید.

    چگونه به طور عملی اختلافات ادغام را حل کنیم¶

    را خواهید دید وقتی ویژوال استودیو یک تداخل را تشخیص می‌دهد، یک ویرایشگر ادغام باز می‌کند. معمولاً قسمت‌های Current ، Incoming و Result .

    • Current : نسخه‌ای که در حال حاضر در شاخه‌ای که در آن هستید، قرار دارد.
    • ورودی : نسخه‌ای از شاخه‌ای که قرار است ادغام شود
    • نتیجه : کد نهایی که باید تأیید کنید

    انتخاب کنید:

    • فعلی، وقتی کد از قبل در شاخه فعلی شما باشد، صحیح است
    • ورودی می‌آید وقتی کد شاخه‌ای که قرار است ادغام شود، صحیح باشد،
    • هر دو فقط زمانی مورد نیاز هستند که هر دو تغییر مورد نیاز و سازگار باشند
    • در صورت نیاز، نتایج را ویرایش کنید. به جای پذیرش کورکورانه یک طرف، به صورت دستی پنل
    آخرین نسخه اصلی را به یک شاخه ویژه بیاورید¶

    شاخه‌های طولانی می‌توانند از شاخه اصلی دور شوند. برای کاهش تداخل‌های بزرگتر در آینده، شاخه خود را مرتباً با آوردن شاخه اصلی به آن به‌روزرسانی کنید. این به شما کمک می‌کند تا مشکلات را در مراحل اولیه، زمانی که شاخه هنوز کوچک است، کشف کنید.

    جریان ویژوال استودیو¶
    • به شاخه ویژگی خود بروید
    • باز کنید مخزن گیت را
    • کلیک راست روی صفحه اصلی
    • را انتخاب کنید ادغام در شاخه فعلی

    اگر تداخلی پیش آمد، به جای به تعویق انداختن، فوراً آن را حل کنید. به‌روزرسانی منظم یک شاخه با main به تشخیص سریع‌تر تداخل‌ها، زمانی که هنوز کوچک هستند و رفع آن‌ها آسان‌تر است، کمک می‌کند.

    نحوه کلون کردن یک پروژه از گیت‌هاب¶

    کلونینگ زمانی استفاده می‌شود که مخزن از قبل در GitHub وجود دارد و شما می‌خواهید یک کپی کامل از آن را روی دستگاه خود داشته باشید. این کار معمولاً زمانی انجام می‌شود که به لپ‌تاپ دیگری نقل مکان می‌کنید یا به یک پروژه موجود می‌پیوندید.

    کلون کردن با استفاده از ویژوال استودیو¶
    1. ویژوال استودیو را باز کنید
    2. بروید به Git → Clone Repository
    3. آدرس مخزن را جایگذاری کنید
    4. پوشه مقصد را در دستگاه خود انتخاب کنید
    5. کلیک کنید روی کلون
    6. پس از اتمام دانلود، راه‌حل را باز کنید
    کلون چه چیزی به شما می‌دهد؟¶
    • تمام فایل‌های پروژه
    • تاریخچه کامل کامیت‌ها
    • اطلاعات اتصال از راه دور
    • ارجاعات شاخه‌ها
    • یک مخزن محلی گیت کاملاً فعال
    بعد از کلونینگ چه اتفاقی می‌افتد؟¶

    پس از اتمام عملیات کلون، می‌توانید برنامه را بسازید، شاخه‌هایی ایجاد کنید، به صورت محلی کامیت کنید، تغییرات جدید را دریافت کنید و در صورت داشتن مجوز، کار خود را ارسال کنید. کلون یک فایل دانلود شده یک‌باره نیست. این یک مخزن کاری کامل با قابلیت Git ایجاد می‌کند.

    اشتباهات رایج مبتدیان و نحوه اجتناب از آنها¶
    • کار مستقیم روی شاخه اصلی: برای هر تغییر واقعی، یک شاخه اختصاصی برای ویژگی‌ها یا رفع اشکالات ایجاد کنید.
    • هل دادن بدون کشیدن اول: آخرین تغییرات را در شروع کار و در صورت نیاز، قبل از آخرین هل دادن، اعمال کنید.
    • کامیت‌های بزرگ: واحدهای منطقی کوچک کار را با پیام‌های واضح کامیت کنید.
    • کامیت کردن فایل‌های تولید شده: از .gitignore به درستی استفاده کنید و فایل‌ها را قبل از اولین ارسال بررسی کنید.
    • حل کورکورانه‌ی اختلافات: کد را با دقت بخوانید و به جای پذیرش کورکورانه‌ی یک طرف، نتیجه‌ی نهایی درست را ارائه دهید.
    • فراموش کردن تست بعد از ادغام: پروژه را بعد از هر ادغام معنادار، بسازید، اجرا کنید و تست کنید.
    • افشای اسرار: هرگز رمزهای عبور، کلیدهای دسترسی، PATها یا رشته‌های اتصال در محیط عملیاتی را افشا نکنید.
    نتیجه‌گیری:¶

    وقتی یادگیرنده گیت‌هاب را در جریان یک پروژه واقعی به جای دستورات مجزا ببیند، درک آن بسیار آسان‌تر می‌شود. در این مثال عملی، ما یک پروژه جدید ASP.NET Core Web API ایجاد کردیم، آن را به عنوان یک مخزن محلی گیت تنظیم کردیم، اولین کامیت را انجام دادیم، آن را به گیت‌هاب متصل کردیم، آن را به گیت‌هاب ارسال کردیم و سپس با استفاده از یک شاخه ویژگی، یک شاخه رفع اشکال، عملیات ادغام و حل تعارض، توسعه حرفه‌ای را ادامه دادیم. این چرخه حیات توسعه واقعی است که مبتدیان باید آن را درک کنند.

    از اینجا به بعد، روال سیستماتیک می‌شود: آخرین تغییرات را دریافت کنید، به‌روزرسانی‌های منطقی کوچک انجام دهید، با دقت مرحله‌بندی کنید، به وضوح کامیت کنید، مرتباً ارسال کنید، برای کارهای معنادار شاخه ایجاد کنید، با دقت ادغام کنید، تداخل‌ها را هوشمندانه حل کنید و بعد از هر ادغام مهم، تست کنید. وقتی این نظم به یک عادت تبدیل شود، گیت و گیت‌هاب دیگر احساس پیچیدگی نمی‌کنند و به بخش‌های ایمن و قابل اعتماد توسعه نرم‌افزار حرفه‌ای تبدیل می‌شوند.
