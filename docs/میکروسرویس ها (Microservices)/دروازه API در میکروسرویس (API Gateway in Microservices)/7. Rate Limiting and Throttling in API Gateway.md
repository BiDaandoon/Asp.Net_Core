
## **محدود کردن نرخ و تنظیم سرعت در API Gateway**

در یک سیستم توزیع‌شده مدرن مانند **معماری میکروسرویس‌ها**، API Gateway شما به عنوان نقطه ورود به ده‌ها میکروسرویس، از جمله UserService، OrderService و ProductService عمل می‌کند. هنگامی که صدها یا هزاران کاربر، برنامه‌های تلفن همراه، تب‌های مرورگر یا حتی ربات‌ها سعی می‌کنند به طور همزمان به APIهای شما دسترسی پیدا کنند، باعث ایجاد **ترافیک بیش از حد (Traffic Overload)** می‌شود.

اگر یک کلاینت، چه به صورت تصادفی و چه عمدی، درخواست‌های زیادی را در مدت زمان کوتاهی ارسال کند، سیستم شما می‌تواند **از کار بیفتد**، **کند شود** یا **برای سایر کاربران در دسترس نباشد**. اینجاست که **محدودیت سرعت (Rate Limiting)** و **تنظیم سرعت (Throttling)** وارد عمل می‌شوند. این دو تکنیک به API Gateway شما کمک می‌کنند تا به عنوان یک کنترل‌کننده هوشمند ترافیک عمل کند و تضمین کند که سرویس‌های backend **سالم**، **در دسترس** و **به طور منصفانه به اشتراک گذاشته** می‌شوند.

#### **محدود کردن نرخ چیست؟**

**محدود کردن نرخ** به معنای تعریف تعداد درخواست‌هایی است که یک کلاینت مجاز به ارسال آنها در یک دوره زمانی ثابت است. به عنوان مثال، ممکن است تصمیم بگیرید که هر کلاینت **فقط می‌تواند ۱۰۰ درخواست در دقیقه** ارسال کند. اگر یک کاربر یا برنامه سعی کند از این محدودیت فراتر رود، Gateway به سادگی درخواست‌های بیشتر را برای آن دقیقه مسدود کرده و پاسخ واضحی ارسال می‌کند:

- **HTTP 429 - درخواست‌های بسیار زیاد**

این مکانیزم تضمین می‌کند که **هیچ کاربری نمی‌تواند تمام منابع موجود را مصرف کند** و همه سهم منصفانه‌ای از ظرفیت سیستم را دریافت می‌کنند.

می‌توانید محدودیت سرعت را مانند **محدودیت سرعت در بزرگراه** در نظر بگیرید: اگر خیلی سریع رانندگی کنید (درخواست‌های زیادی ارسال کنید)، جریمه می‌شوید (خطای ۴۲۹). این یک قانون سختگیرانه است؛ وقتی از حد مجاز فراتر بروید، باید تا پنجره زمانی بعدی صبر کنید.

#### **تروتلینگ چیست؟**

**محدود کردن ترافیک** کمی متفاوت است. به جای مسدود کردن فوری درخواست‌ها، Gateway **جریان ترافیک** را با **صف‌بندی موقت درخواست‌های اضافی** کنترل می‌کند. این رویکرد در مواقع اوج ترافیک کوتاه‌مدت مفید است، به عنوان مثال، زمانی که یک فروش ویژه شروع می‌شود و همه در همان لحظه روی «همین حالا بخرید» کلیک می‌کنند.

کنترل ترافیک بیشتر شبیه یک **پلیس راهنمایی و رانندگی است که یک تقاطع شلوغ را مدیریت می‌کند**. وقتی تعداد زیادی ماشین (درخواست) می‌رسند، پلیس جاده را به طور کامل نمی‌بندد. آنها جریان را کند می‌کنند و به ماشین‌ها اجازه می‌دهند یکی یکی عبور کنند تا ترافیک با خیال راحت حرکت کند. API Gateway نیز همین کار را انجام می‌دهد. بدون رد کردن هر درخواست اضافی، افزایش ناگهانی سرعت را کاهش می‌دهد.

#### **چرا هر دو مهم هستند؟**

محدود کردن نرخ و تنظیم سرعت، فقط اقدامات امنیتی نیستند؛ بلکه **ابزارهای ضروری برای حفظ سلامت و پایداری API** هستند. آن‌ها در کنار هم،:

- جلوگیری از **سرور** اضافه بار و **خرابی**،
- سیستم را **در ترافیک بالا پاسخگو** نگه دارید،
- اطمینان از **استفاده منصفانه** در بین همه مشتریان، و
- محافظت از سرویس‌ها در برابر **ربات‌های مخرب یا سوءاستفاده‌های تصادفی**.

این دو مفهوم فقط مربوط به امنیت نیستند؛ بلکه ابزارهای ضروری برای حفظ **سلامت API، انصاف و قابلیت اطمینان** در هر سیستم میکروسرویس جدی هستند.

#### **چرا به محدود کردن نرخ و تنظیم سرعت نیاز داریم؟**

در **معماری میکروسرویس**، چندین کلاینت، برنامه‌های وب، برنامه‌های موبایل، سیستم‌های همکار و ادغام‌های شخص ثالث، همگی به طور همزمان درخواست‌های API ارسال می‌کنند. اگرچه این نشانه‌ای از تعامل بالا است، اما وقتی یک کلاینت واحد **درخواست‌های زیادی را در مدت زمان کوتاهی** ارسال می‌کند، می‌تواند خطرناک شود.

این می‌تواند از چند طریق اتفاق بیفتد:

- یک توسعه‌دهنده یک حلقه بی‌نهایت می‌نویسد که مدام API شما را فراخوانی می‌کند.
- کاربر در حالی که منتظر پاسخ است، بارها و بارها برنامه را رفرش می‌کند.
- یک رقیب یا ربات سعی می‌کند عمداً سرویس شما را بیش از حد بارگذاری کند.
- یک رویداد فروش یا تبلیغاتی باعث افزایش ناگهانی ترافیک می‌شود.

بدون کنترل‌های مناسب، این موقعیت‌ها می‌توانند منجر به موارد زیر شوند:

- **سربار سرویس یا خرابی‌ها**: سرورهای بک‌اند شما دچار سربار می‌شوند و دیگر پاسخ نمی‌دهند.
- **افزایش تأخیر (زمان پاسخ)**: بار سنگین یک کاربر، زمان پاسخ‌دهی را برای همه کاربران دیگر کاهش می‌دهد.
- **هزینه‌های بالای زیرساخت**: سرورها به دلیل بار غیرقابل تنظیم، به سرعت در حال افزایش ظرفیت هستند.
- **خرابی کامل**: در بدترین حالت، کل سیستم شما آفلاین می‌شود.

اینجاست که محدودیت نرخ (Rate Limiting) و تنظیم سرعت (Throttling) به کار می‌آیند.

**محدود کردن نرخ،** را تضمین می‌کند **با تعیین محدودیت برای هر کاربر، آدرس IP، کلید API، شناسه کلاینت یا توکن احراز هویت، استفاده منصفانه**. به هر کلاینت سهمیه منصفانه‌ای داده می‌شود، به عنوان مثال، ۱۰۰ درخواست در دقیقه.

**کنترل سرعت،** تضمین می‌کند **جریان ترافیک روان را**. به جای رد کردن هر درخواست اضافی، آنها را در صف قرار می‌دهد یا کمی به تأخیر می‌اندازد. به این ترتیب، سرویس‌های شما تحت فشار از کار نمی‌افتند و کلاینت‌ها حتی در هنگام بار سنگین، پاسخ‌های قابل پیش‌بینی و پایداری را تجربه می‌کنند.

آنها با هم، سیستم شما را از موارد زیر محافظت می‌کنند:

- **حملات DDoS (انکار سرویس)**، که در آن مهاجمان API های شما را با درخواست های فراوان پر می کنند.
- **استفاده بیش از حد تصادفی زمانی اتفاق می‌افتد** که کاربران واقعی ناخواسته درخواست‌های زیادی ارسال می‌کنند.
- **افزایش ناگهانی ترافیک**، مانند زمان فروش‌های ویژه یا رونمایی از محصولات جدید.
- **بی‌ثباتی سیستم**، تضمین سلامت و پاسخگویی سرویس‌های backend.

به طور خلاصه، محدود کردن نرخ و تنظیم سرعت، API های شما را **ایمن، مقیاس پذیر و پایدار** نگه می دارد.

#### **محدود کردن نرخ و تنظیم سرعت چگونه کار می‌کند؟**

بیایید فرآیند را گام به گام تجزیه کنیم تا بفهمیم API Gateway چگونه ترافیک ورودی را مدیریت می‌کند.

##### **مرحله ۱ - دریافت درخواست‌ها**

هر درخواست ورودی ابتدا از طریق **API Gateway** عبور می‌کند که به عنوان نقطه ورود واحد برای همه کلاینت‌ها عمل می‌کند.

##### **مرحله ۲ - شناسایی مشتری**

دروازه، درخواست‌کننده را شناسایی می‌کند و از ویژگی‌هایی مانند موارد زیر استفاده می‌کند:

- **آدرس IP** (برای کلاینت‌های ناشناس)
- **شناسه کاربری از توکن JWT** (برای کاربران وارد شده)

این به سیستم کمک می‌کند تا فعالیت هر کلاینت را جداگانه پیگیری کند.

##### **مرحله ۳ - شمارش درخواست‌ها**

دروازه (Gateway) شمارنده‌ای از تعداد درخواست‌هایی که کلاینت در یک دوره زمانی خاص (مثلاً ۶۰ ثانیه آخر) انجام داده است را نگه می‌دارد. این تعداد می‌تواند در حافظه یا در یک حافظه پنهان توزیع‌شده، مانند **Redis،** در صورت اجرای چندین سرور دروازه، ذخیره شود.

##### **مرحله ۴ – اعمال محدودیت**

اگر تعداد درخواست‌های کلاینت **در محدوده مجاز** باشد، Gateway درخواست را به میکروسرویس مناسب (مانند ProductService یا PaymentService) ارسال می‌کند. اما اگر از این محدوده **تجاوز شود**، یکی از دو اتفاق زیر رخ می‌دهد:

**محدود کردن نرخ:** دروازه درخواست را فوراً مسدود می‌کند و با ... پاسخ می‌دهد.

- HTTP/1.1 429 درخواست‌های بسیار زیاد
- دوباره امتحان کردن - بعد از: 30

این یعنی به محدودیت زمانی رسیده‌اید. بعد از 30 ثانیه دوباره امتحان کنید. کلاینت نیازی به مدیریت خاصی ندارد؛ مرورگرهای مدرن و کلاینت‌های API این موضوع را به‌طور خودکار درک می‌کنند.

**کاهش سرعت (Throttling):** دروازه (Gateway) به طور موقت درخواست را نگه می‌دارد یا پردازش آن را کند می‌کند تا از شلوغ شدن بک‌اند جلوگیری شود.

این فیلترینگ هوشمند تضمین می‌کند که درخواست‌های مشروع به طور روان ادامه می‌یابند و در عین حال به طور خودکار ترافیک غیرمجاز یا بیش از حد را کنترل می‌کند.

#### **مثالی برای درک** **محدودیت نرخ و تنظیم سرعت در API Gateway**

در مثال ما، ما **محدودیت نرخ و تنظیم سرعت را** درون یک **API Gateway ساخته شده با استفاده از Ocelot** در ASP.NET Core پیاده‌سازی خواهیم کرد. هدف، **کنترل و مدیریت تعداد درخواست‌ها** از کلاینت‌ها (وب، موبایل یا سیستم‌های خارجی) به میکروسرویس‌های مختلف مانند **محصول**، **سفارش** و **پرداخت** است تا از بارگذاری بیش از حد جلوگیری شود و استفاده منصفانه تضمین شود.

پیاده‌سازی از موارد زیر استفاده خواهد کرد:

- **محدودکننده نرخ پنجره ثابت** برای محدودیت‌های درخواست مبتنی بر زمان (مثلاً ۱۰۰ درخواست در دقیقه).
- **محدودکننده همزمانی** برای APIهای حساس (مانند پرداخت‌ها) برای کنترل درخواست‌های همزمان.

هر خط‌مشی در appsettings.json تعریف شده است، به همراه قوانین خاص برای تعداد درخواست‌های مجاز در هر دقیقه و تعدادی که می‌توانند در صف انتظار قرار گیرند.

به طور خلاصه، این مثال نشان می‌دهد که چگونه می‌توان با اعمال کنترل‌های هوشمند درخواست (محدود کردن نرخ و تنظیم سرعت) از طریق یک میان‌افزار سفارشی در لایه API Gateway، از میکروسرویس‌های backend محافظت کرد.

##### **مرحله ۱: نصب بسته‌های مورد نیاز**

در ویژوال استودیو، **کنسول مدیریت بسته‌ها (Package Manager Console) را** باز کنید و **پروژه API Gateway** خود را انتخاب کنید (نه میکروسرویس‌های جداگانه). دستور زیر را اجرا کنید:

- **نصب بسته System.Threading.RateLimiting**

این **کتابخانه بومی .NET 8** برای محدود کردن سرعت و تنظیم سرعت است.

##### **مرحله ۲: تعریف پیکربندی در appsettings.json**

بخش «RateLimiting» در appsettings.json را به عنوان **کنترل پنل** یا **آیین‌نامه‌ای** در نظر بگیرید که API Gateway ما برای تصمیم‌گیری در مورد موارد زیر از آن پیروی می‌کند:

- هر کاربر یا IP چند درخواست می‌تواند انجام دهد؟
- ظرف چه مدت زمانی؟
- وقتی به حد نصاب رسید چه اتفاقی می‌افتد؟

این پیکربندی یک بار در هنگام راه‌اندازی خوانده می‌شود، سپس توسط میان‌افزار ما (RateLimitingMiddleware) و سرویس سیاست (RateLimitPolicyService) برای اعمال محدودیت سرعت در زمان اجرا استفاده می‌شود. بنابراین، فایل appsettings.json را باز کنید و این بخش را اضافه کنید:

```json
"RateLimiting": {
  "IsEnabled": true,
  "DefaultPolicy": {
    "PermitLimit": 60,
    "Window": "00:01:00",
    "QueueLimit": 5,
    "QueueProcessingOrder": "OldestFirst"
  },
  "ProductApiPolicy": {
    "PermitLimit": 10,
    "Window": "00:01:00",
    "QueueLimit": 0,
    "QueueProcessingOrder": "OldestFirst"
  },
  "OrderApiPolicy": {
    "PermitLimit": 50,
    "Window": "00:01:00",
    "QueueLimit": 2,
    "QueueProcessingOrder": "OldestFirst"
  },
  "PaymentApiPolicy": {
    "PermitLimit": 5,
    "QueueLimit": 2,
    "QueueProcessingOrder": "OldestFirst"
  }
}
```

##### **توضیح کد:**

###### **فعال شده است**

این ویژگی به عنوان **سوئیچ اصلی** برای کل سیستم محدودکننده نرخ و تنظیم سرعت شما عمل می‌کند.

- وقتی IsEnabled روی **true** تنظیم شده باشد، API Gateway به طور فعال تمام قوانین محدودکننده نرخ تعریف شده تحت هر خط‌مشی را اعمال می‌کند.
- وقتی روی **false** تنظیم شود، محدودیت نرخ به طور کامل غیرفعال می‌شود. میان‌افزار از NoRateLimiter استفاده می‌کند که به هر درخواستی اجازه می‌دهد بدون محدودیت عبور کند.
- این امر باعث می‌شود که توسعه‌دهندگان یا مدیران بتوانند به راحتی و بدون نیاز به حذف یا کامنت‌گذاری هیچ کدی، به طور موقت کنترل سرعت را برای اشکال‌زدایی یا تعمیر و نگهداری غیرفعال کنند.
- این قابلیت **، انعطاف‌پذیری در سطح محیط** را فراهم می‌کند، بنابراین می‌توانید محدودیت سرعت را در محیط‌های توسعه و آزمایش غیرفعال اما در محیط عملیاتی فعال نگه دارید.

###### **محدودیت مجوز**

این ویژگی **حداکثر تعداد درخواست‌های مجاز** برای یک هویت واحد (UserId یا آدرس IP) را در یک بازه زمانی مشخص تعریف می‌کند.

- این «ظرفیت» یا تعداد درخواست‌هایی را که یک کاربر یا کلاینت می‌تواند قبل از مسدود شدن موقت انجام دهد، تعیین می‌کند.
- زمانی که تعداد درخواست‌ها از این حد فراتر رود، درخواست‌های بیشتر یا در صف قرار می‌گیرند (در صورت وجود محدودیت صف) یا بلافاصله با **پاسخ HTTP 429 Too Many Requests** رد می‌شوند.
- این امر با محدود کردن درخواست‌های پشت سر هم بیش از حد، به محافظت از سرویس‌های پایین‌دستی شما در برابر اضافه بار کمک می‌کند.
- مقدار مناسب به ترافیک مورد انتظار API شما بستگی دارد، برای مثال:
  - APIهای محصول (عمدتاً فقط خواندنی) می‌توانند محدودیت‌های بالاتری مانند ۱۰۰ در دقیقه داشته باشند.
  - APIهای پرداخت یا رزرو (عملیات سنگین نوشتن) باید محدودیت‌های کمتری داشته باشند، مانند ۵ یا ۱۰ در دقیقه.

**مثال:** اگر «PermitLimit» برابر با ۶۰ باشد، هر کاربر یا IP می‌تواند **در هر پنجره ۱ دقیقه‌ای ۶۰ درخواست** ارسال کند.

###### **پنجره**

این ویژگی، **بازه زمانی یا مدت زمانی** را که سیستم در آن PermitLimit را ردیابی و اعمال می‌کند، تعریف می‌کند.

- این به Rate Limiter می‌گوید **چه مدت درخواست‌های ورودی را بشمارد.** که قبل از تنظیم مجدد شمارنده،
- قالب از الگوی استاندارد hh:mm:ss (ساعت، دقیقه، ثانیه) پیروی می‌کند.
- پس از پایان بازه زمانی، شمارنده درخواست‌ها ریست می‌شود و کاربران می‌توانند دسته جدیدی از درخواست‌ها را ارسال کنند.
- برای مثال، پنجره‌ای با مقدار «۰۰:۰۱:۰۰» به این معنی است که محدودکننده سرعت، درخواست‌ها را در هر دقیقه شمارش می‌کند.

**مثال مورد استفاده:** اگر "PermitLimit": 60 و "Window": "00:01:00" باشد، هر کاربر می‌تواند **60 درخواست در دقیقه ارسال کند. پس از** یک دقیقه، تعداد درخواست‌های آنها به طور خودکار تنظیم مجدد می‌شود.

###### **محدودیت صف**

این ویژگی **حداکثر تعداد درخواست‌هایی را که می‌توانند در صف انتظار بمانند،** زمانی که همه مجوزهای موجود تمام شده باشند، مشخص می‌کند.

- وقتی کاربری به PermitLimit می‌رسد، درخواست‌های اضافی بلافاصله رد نمی‌شوند؛ بلکه در صف انتظار قرار می‌گیرند.
- اگر تعداد درخواست‌های در انتظار از QueueLimit بیشتر شود، درخواست‌های جدید با پاسخ 429 Too Many Requests رد می‌شوند.
- این امر با اجازه دادن به چند درخواست اضافی برای منتظر ماندن به جای حذف فوری، به کاهش افزایش ناگهانی ترافیک کمک می‌کند.
- تنظیم این مقدار روی مقادیر خیلی بالا ممکن است زمان پاسخ‌دهی را تحت بار افزایش دهد؛ تنظیم خیلی پایین آن نیز ممکن است باعث رد شدن زودهنگام شود.

**مثال:** اگر «QueueLimit» برابر با ۵ باشد، پس از رسیدن به ۶۰ درخواست (PermitLimit)، **پنج درخواست دیگر می‌توانند منتظر بمانند** تا سیستم شروع به رد درخواست‌های جدید کند.

###### **ترتیب پردازش صف**

این ویژگی **ترتیب پردازش درخواست‌های در صف انتظار را** پس از در دسترس قرار گرفتن مجدد مجوزها تعریف می‌کند.

- این کنترل می‌کند که سیستم چگونه تصمیم می‌گیرد **کدام درخواست منتظر ابتدا ارائه شود**.
- گزینه‌های ممکن عبارتند از:
  - «قدیمی‌ترین‌ها» → درخواست‌ها را به همان ترتیبی که رسیده‌اند پردازش می‌کند (اولین-ورودی، اولین-خروجی).
  - «جدیدترین‌ها» → اولویت را به جدیدترین درخواست‌ها می‌دهد (آخرین ورودی، اولین خروجی).
- در اکثر APIها، «OldestFirst» ترجیح داده می‌شود تا انصاف رعایت شود و از هدر رفتن درخواست‌های قبلی توسط درخواست‌های جدیدتر جلوگیری شود.
- این تنظیم فقط زمانی فعال می‌شود که به دلیل محدودیت‌های مجوز، درخواست‌ها در صف انتظار قرار داشته باشند.

**مثال:** اگر «QueueProcessingOrder»: «OldestFirst»، محدودکننده همیشه **اولین درخواست انتظار را اول مدیریت می‌کند.** وقتی یک اسلات خالی می‌شود،

###### **بخش‌های سیاست (سیاست پیش‌فرض، سیاست رابط برنامه‌نویسی محصول، سیاست رابط برنامه‌نویسی سفارش، سیاست رابط برنامه‌نویسی پرداخت)**

هر بخش از سیاست، **مجموعه‌ای از قوانین جداگانه را** برای دسته خاصی از APIها در Gateway شما نشان می‌دهد.

- **DefaultPolicy** به عنوان یک جایگزین برای مسیرهایی عمل می‌کند که با هیچ دسته خاصی مطابقت ندارند.
- **سیاست محصول (ProductApiPolicy)** قوانینی را برای APIهای مرتبط با محصول تعریف می‌کند که معمولاً به دلیل مدیریت ترافیک سنگین خواندن، تحمل بیشتری دارند.
- **سیاست OrderApiPolicy** روی نقاط پایانی پردازش سفارش اعمال می‌شود و به دلیل حساسیت تراکنش‌ها، کنترل کمی سخت‌گیرانه‌تری ارائه می‌دهد.
- **PaymentApiPolicy** سختگیرانه‌ترین است و اغلب از محدودیت‌های مبتنی بر همزمانی استفاده می‌کند، زیرا عملیات پرداخت باید سریالی شده یا به شدت تحت کنترل نرخ باشند.

**مثال جریان:** اگر کاربری درخواستی را به /api/orders/create ارسال کند، میان‌افزار به‌طور خودکار تشخیص می‌دهد که این درخواست تحت **OrderApiPolicy** قرار می‌گیرد و از محدودیت‌های خاص آن استفاده می‌کند.

##### **مرحله ۳: ایجاد کلاس‌های مدل**

به **کلاس RateLimitSettings** عنوان **پلی بین فایل پیکربندی ما (appsettings.json)** و **منطق زمان اجرا** (middleware و services) عمل می‌کند. به راحتی در سراسر کدبیس ما قابل دسترسی باشند در .NET **این کلاس تضمین می‌کند که تنظیمات محدودکننده نرخ تعریف شده در appsettings.json به طور قوی تایپ شده و با استفاده از الگوی Options** .

به طور خلاصه، کلاس RateLimitSettings قوانین محدودکننده نرخ و نحوه اعمال آنها برای هر دسته API را تعریف می‌کند. بنابراین، یک فایل کلاس به نام **RateLimitSettings.cs** در **پوشه Models** ایجاد کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
namespace APIGateway.Models
{
    // Represents the global rate limiting configuration.
    // This model maps directly to the "RateLimiting" section in appsettings.json.
    public class RateLimitSettings
    {
        // Enables or disables rate limiting globally.
        // When false, the middleware bypasses all limiter checks (uses NoopRateLimiter).
        public bool IsEnabled { get; set; }

        // Default global policy applied to all endpoints
        // that do not have a specific API policy defined.
        public Policy DefaultPolicy { get; set; } = new();

        // Rate limiting rules specifically for Product-related APIs.
        // Example: /api/products/*
        public Policy ProductApiPolicy { get; set; } = new();

        // Rate limiting rules specifically for Order-related APIs.
        // Example: /api/orders/*
        public Policy OrderApiPolicy { get; set; } = new();

        // Rate limiting rules specifically for Payment-related APIs.
        // Example: /api/payments/*
        // Typically configured with a stricter limit
        // since payment operations are sensitive and require throttling.
        public Policy PaymentApiPolicy { get; set; } = new();

        // Inner class representing an individual rate limiting policy.
        // Each policy defines how many requests can be made in a specific time window
        // and how excess requests are queued or rejected.
        public class Policy
        {
            // Maximum number of requests permitted within a given time window.
            // Example: PermitLimit = 100 means 100 requests per window per user/IP.
            public int PermitLimit { get; set; }

            // The duration of the fixed or sliding window.
            // Format: "hh:mm:ss" (e.g., "00:01:00" = 1 minute window).
            public string Window { get; set; } = "00:01:00";

            // The number of requests that can wait in the queue
            public int QueueLimit { get; set; }

            // The order in which queued requests are processed:
            // "OldestFirst" → FIFO (first-come, first-served)
            // "NewestFirst" → LIFO (newest request gets priority)
            // This maps to the QueueProcessingOrder enum in System.Threading.RateLimiting.
            public string QueueProcessingOrder { get; set; } = "OldestFirst";
        }
    }
}
```

#### **RateLimitPolicy شمارشی**

شمارشگر RateLimitPolicy نشان‌دهنده **دسته‌ها یا گروه‌های مختلف APIها** در Gateway ما است که هر کدام **رفتار محدودکننده نرخ خود را** دارند. به جای کدگذاری رشته‌هایی مانند «ProductApiPolicy» یا «OrderApiPolicy» در سراسر کد، یک **شمارشگر strongly typed** تعریف می‌کنیم که بیان می‌کند کدام سیاست برای کدام مسیر اعمال می‌شود.

متغیر شمارشی RateLimitPolicy به API Gateway می‌گوید **که کدام مجموعه قوانین را** برای هر درخواست ورودی اعمال کند و تضمین کند که هر مسیر (محصولات، سفارشات، پرداخت‌ها و غیره) از سیاست محدودکننده نرخ صحیح تعریف شده در فایل پیکربندی شما پیروی می‌کند. بنابراین، یک فایل کلاس به نام **RateLimitPolicy.cs** در **پوشه Models** ایجاد کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
namespace APIGateway.Models
{
    // Each enum value corresponds to a specific configuration section
    // inside the RateLimiting section of appsettings.json file.
    // Example (JSON):
    // "RateLimiting": {
    //   "DefaultPolicy": { ... },
    //   "ProductApiPolicy": { ... },
    //   "OrderApiPolicy": { ... },
    //   "PaymentApiPolicy": { ... }
    // }

    public enum RateLimitPolicy
    {
        Default,
        ProductApi,
        OrderApi,
        PaymentApi
    }
}
```

#### **درک RateLimiter و RateLimitLease:**

این دو ( **RateLimiter** و **RateLimitLease** ) **بلوک‌های سازنده‌ی اصلی** سیستم **محدودکننده‌ی نرخ بومی .NET 8** هستند.

##### **محدودکننده نرخ چیست؟**

**RateLimiter** یک **کلاس پایه انتزاعی** در .NET است که قوانین و رفتار را برای کنترل تعداد درخواست‌هایی که می‌توانند در یک دوره زمانی خاص انجام شوند، تعریف می‌کند. این کلاس مانند یک **کنترل‌کننده ترافیک** است که تضمین می‌کند درخواست‌های زیادی به طور همزمان پردازش نشوند و از اضافه بار سیستم، سوءاستفاده از API یا فرسودگی منابع جلوگیری کند.

##### **نحوه عملکرد کلی RateLimiter**

وقتی درخواستی می‌رسد:

1. محدودکننده بررسی می‌کند **چند درخواست ارسال شده است.** که اخیراً
2. تصمیم می‌گیرد که آیا **مجاز**، **به تأخیر بیندازد** یا **رد کند.** درخواست جدید را
3. این تابع یک **RateLimitLease** برمی‌گرداند، توکنی که نشان می‌دهد آیا درخواست پذیرفته شده است یا خیر.
4. فراخواننده (میان‌افزار یا کد برنامه) بر این اساس عمل می‌کند: یا درخواست را پردازش می‌کند یا پاسخ HTTP 429 (درخواست‌های بیش از حد) را برمی‌گرداند.

##### **محدودیت نرخ اجاره (RateLimitLease) چیست؟**

RateLimitLease **نتیجه بررسی Rate-Limit را** نشان می‌دهد. این پارامتر مشخص می‌کند که آیا درخواست فعلی مجاز بوده یا رد شده است. این پارامتر مانند **برگه مجوز** یا **مجوز ورود** صادر شده توسط RateLimiter است.

##### **ایجاد کمک‌کننده بدون محدودیت نرخ:**

کلاس NoRateLimiter یک **پیاده‌سازی سفارشی از** **کلاس پایه‌ی داخلی RateLimiter در .NET** است. این کلاس به گونه‌ای طراحی شده است که **هیچ کاری انجام ندهد**، یعنی **بلافاصله به هر درخواستی اجازه دهد.** همیشه بدون اعمال هیچگونه محدودیت، شمارش یا صف‌بندی،

این زمانی استفاده می‌شود که پیکربندی سراسری (IsEnabled = false در appsettings.json) می‌گوید: «من نمی‌خواهم در حال حاضر هیچ محدودیت نرخی اعمال کنم.» بنابراین به جای حذف کامل میان‌افزار محدودکننده نرخ یا اضافه کردن ده‌ها بررسی if (IsEnabled) در سراسر کد، **محدودکننده عادی را با** **این یکی عوض می‌کنیم.**

ابتدا، پوشه‌ای به نام Helpers در دایرکتوری ریشه پروژه لایه API Gateway ایجاد کنید. سپس، یک فایل کلاس به نام **NoRateLimiter.cs** در **پوشه Helpers** ایجاد کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
using System.Threading.RateLimiting;

namespace APIGateway.Helpers
{
    // Used when global rate limiting is turned off (IsEnabled = false).
    // Always allows requests without applying any throttling.
    public sealed class NoRateLimiter : RateLimiter
    {
        // Reusable "always-allowed" lease for all requests.
        private static readonly RateLimitLease _lease = new NoLease();

        // Indicates the limiter is always active (never idle).
        public override TimeSpan? IdleDuration => Timeout.InfiniteTimeSpan;

        // Synchronously grants permission for every request.
        protected override RateLimitLease AttemptAcquireCore(int permitCount)
        {
            return _lease;
        }

        // Asynchronous method that grants permission immediately for all requests.
        // Used when rate limiting is globally disabled.
        protected override ValueTask<RateLimitLease> AcquireAsyncCore(
            int permitCount,
            CancellationToken cancellationToken)
        {
            // Always returns a successful lease without any delay or throttling.
            return new ValueTask<RateLimitLease>(_lease);
        }

        // No statistics tracking for this limiter.
        public override RateLimiterStatistics? GetStatistics()
        {
            return null;
        }

        // Represents a successful lease that always allows requests.
        private sealed class NoLease : RateLimitLease
        {
            // Always grants permission.
            public override bool IsAcquired => true;

            // No metadata (e.g., retry info) is provided.
            public override IEnumerable<string> MetadataNames => Array.Empty<string>();

            // Always returns false since no metadata exists.
            public override bool TryGetMetadata(string name, out object? metadata)
            {
                metadata = null;
                return false;
            }
        }
    }
}
```

##### **محدودیت نرخ اجاره (RateLimitLease) چیست؟**

یک **RateLimitLease** نشان دهنده یک « **برگه مجوز** » است که تعیین می‌کند آیا یک درخواست اجازه ادامه دارد یا خیر.

- هر بار که درخواستی از طرف کلاینت می‌رسد، محدودکننده نرخ باید تصمیم بگیرد که «آیا می‌توانم این درخواست را مجاز بدانم یا خیر؟»
- برگردانده می‌شود **این تصمیم به عنوان یک شیء RateLimitLease** .
- اگر IsAcquired = true باشد، درخواست می‌تواند ادامه یابد؛ در غیر این صورت، درخواست رد می‌شود (معمولاً با وضعیت ۴۲۹ Too Many Requests).
- در **NoRateLimiter** ، اجاره همیشه اعطا می‌شود، زیرا تنظیم سرعت غیرفعال است.
- نمونه \_lease **مجدداً مورد استفاده قرار می‌گیرد و آن را سبک و از نظر thread-safe می‌کند.** برای صرفه‌جویی در حافظه و کاهش تخصیص شیء،

**به این صورت در نظر بگیرید:** هر درخواست API باید یک « **کارت مجوز** » را نشان دهد. اگر کارت (اجاره) معتبر باشد → دروازه باز می‌شود. اگر نامعتبر باشد → درخواست متوقف می‌شود.

##### **مدت زمان بیکاری چیست؟**

ویژگی **IdleDuration** مدت زمانی را که محدودکننده قبل از ریست شدن یا غیرفعال شدن، بیکار بوده است، نشان می‌دهد.

- در محدودکننده‌های معمولی، این به ردیابی زمان تنظیم مجدد شمارنده‌ها یا بازیافت منابع کمک می‌کند.
- در NoRateLimiter، هیچ مفهوم تنظیم مجددی وجود ندارد، همیشه فعال است.
- به همین دلیل است که Timeout.InfiniteTimeSpan را برمی‌گرداند، که به معنای واقعی کلمه به معنای «هرگز بیکار نمانید» است.
- این به فریم‌ورک سیگنال می‌دهد که محدودکننده مکث نمی‌کند، منقضی نمی‌شود یا از کار نمی‌افتد، بلکه به‌طور دائم در دسترس است.

**اینطور تصور کنید:** نگهبانی که هرگز نمی‌خوابد، همیشه بیدار است و همیشه به مردم اجازه عبور می‌دهد.

##### **تابع ()AttemptAcquireCore چیست؟**

این **روش همگام‌سازی** است که برای درخواست مجوز از محدودکننده استفاده می‌شود.

- این تابع زمانی فراخوانی می‌شود که درخواستی دریافت می‌کنید و می‌خواهید فوراً و بدون انتظار، پاسخ بله/خیر دریافت کنید.
- در محدودکننده‌های واقعی، این روش قبل از تصمیم‌گیری، میزان مصرف فعلی، تعداد و محدودیت‌ها را بررسی می‌کند.
- در NoRateLimiter، فقط شیء \_lease قابل استفاده مجدد را برمی‌گرداند، به این معنی که هر درخواست فوراً تأیید می‌شود.
- پارامتر permitCount (تعداد توکن‌های درخواستی) نادیده گرفته می‌شود، زیرا همه درخواست‌ها پذیرفته می‌شوند.

**اینطور تصور کنید:** کسی در می‌زند → نگهبان فوراً و بدون بررسی هیچ چیز، به او اجازه عبور می‌دهد.

##### **تابع ()AcquireAsyncCore چیست؟**

این **نسخه ناهمزمان** AttemptAcquireCore() است که زمانی استفاده می‌شود که محدودکننده ممکن است نیاز داشته باشد برای یک اسلات موجود منتظر بماند (مثلاً وقتی صف‌بندی مطرح است).

- در اکثر محدودکننده‌های دنیای واقعی، این روش درخواست را تا زمانی که یک اسلات باز شود، متوقف می‌کند.
- اما در NoRateLimiter، هیچ انتظار یا صف‌بندی وجود ندارد، محدودکننده همیشه بلافاصله تأیید می‌کند.
- از این رو، به سادگی یک ValueTask حاوی \_lease قابل استفاده مجدد که دسترسی را اعطا می‌کند، برمی‌گرداند.

**اینطور به آن فکر کنید:** حتی اگر سعی کنید منتظر جایی بمانید، دربان فوراً می‌گوید: «نیازی نیست منتظر بمانید، می‌توانید مستقیماً وارد شوید.»

##### **تابع GetStatistics() چیست؟**

متد GetStatistics **()** بینش‌هایی در مورد عملکرد محدودکننده در زمان اجرا ارائه می‌دهد، مانند:

- تعداد مجوزهای اخذ شده
- تعداد درخواست‌های رد شده
- طول صف یا میانگین زمان انتظار

اما از آنجایی که NoRateLimiter هرگز چیزی را ردیابی یا محدود نمی‌کند، داده‌ای را جمع‌آوری نمی‌کند. بنابراین، همیشه مقدار null را برمی‌گرداند، به این معنی که «هیچ آماری در دسترس نیست».

**به این فکر کنید:** سیستمی که هرگز لاگ‌ها را نگه نمی‌دارد زیرا همه چیز همیشه مجاز است.

##### **کلاس NoLease تو در تو**

کلاس NoLease «مجوز» واقعی بازگردانده شده هنگام تأیید درخواست را تعریف می‌کند.

- این متد از RateLimitLease ارث‌بری می‌کند و ویژگی‌های کلیدی آن را لغو می‌کند.
- از آنجایی که این یک اجاره «همیشه موفق» است، فراداده‌ها، محدودیت‌ها یا زمان‌های تلاش مجدد را ردیابی نمی‌کند.
- این صرفاً یک پرچم موفقیت (IsAcquired = true) است که نشان می‌دهد درخواست بدون محدودیت پذیرفته شده است.

**به آن اینطور فکر کنید:** یک «کارت دسترسی» از پیش امضا شده و قابل استفاده مجدد که برای همیشه معتبر است، بدون تاریخ انقضا، بدون داده، بدون محدودیت.

##### **IsAcquired چیست؟**

ویژگی IsAcquired نشان می‌دهد که آیا درخواست فعلی با موفقیت مجوز دریافت کرده است یا خیر.

- در محدودکننده‌های معمولی، IsAcquired = false به این معنی است که به حد مجاز رسیده‌ایم و درخواست باید منتظر بماند یا رد شود.
- در این حالت، این همیشه درست است، به این معنی که هر درخواستی به طور خودکار چراغ سبز دریافت می‌کند.

**اینطور در نظر بگیرید:** هر بازدیدکننده به‌طور خودکار مهر «تایید شده» را روی کارت ورود خود دریافت می‌کند.

##### **نام‌های متادیتا چیست؟**

MetadataNames اطلاعات اضافی ضمیمه شده به اجاره نامه را در خود جای داده است، مانند:

- «بعد از تلاش مجدد» → مدت زمان انتظار قبل از تلاش مجدد
- «مجوزهای باقی‌مانده» → تعداد درخواست‌هایی که هنوز می‌توان در این پنجره ارسال کرد

اما NoRateLimiter از هیچ فراداده‌ای استفاده نمی‌کند و آن را در معرض نمایش قرار نمی‌دهد. از این رو، صرفاً یک لیست خالی برمی‌گرداند.

**به آن فکر کنید مانند:** یک کارت دسترسی که هیچ فیلد اضافی ندارد - فقط "تأیید شده".

##### **تابع ()TryGetMetadata چیست؟**

تابع ()TryGetMetadata برای بازیابی مقادیر خاص فراداده بر اساس کلید استفاده می‌شود. برای مثال، یک محدودکننده واقعی می‌تواند مقادیر زیر را برگرداند:

- «بعد از امتحان دوباره» → ۳۰ ثانیه
- «درخواست‌های باقیمانده» → ۵

در NoRateLimiter، از آنجایی که هیچ چیزی ردیابی یا به تأخیر نمی‌افتد، **هیچ ابرداده‌ای برای بازگشت** وجود ندارد؛ همیشه مقدار نادرست (false) را برمی‌گرداند.

**اینطور در نظر بگیرید:** از نگهبان می‌پرسید: «کی می‌توانم برگردم؟» و او پاسخ می‌دهد: «همیشه اجازه داری، نیازی نیست منتظر بمانی.»

##### **چرا به این «بدون محدودیت نرخ» نیاز داریم؟**

در یک API Gateway در محیط عملیاتی، موقعیت‌هایی وجود دارد که ممکن است بخواهیم **محدودیت نرخ را به طور موقت غیرفعال کنیم**، مانند:

- در طول **تست بار** یا **تست استرس**، ما نمی‌خواهیم که تنظیم سرعت (throttling) تداخل ایجاد کند.
- هنگام **اشکال‌زدایی یا پروفایل‌بندی** عملکرد.
- وقتی **محدودیت‌های نرخ به صورت خارجی کنترل می‌شوند** (مثلاً توسط یک پروکسی معکوس مانند Nginx یا Cloudflare).
- هنگام اجرا در **محیط‌های توسعه یا مرحله‌بندی**، شما نمی‌خواهید توسعه‌دهندگان را با محدودیت‌های مصنوعی کند کنید.

##### **انواع محدودکننده نرخ؟**

مکانیسم‌های محدودکننده سرعت را می‌توان بر اساس **نحوه کنترل جریان درخواست‌ها** به سیستم، به طور گسترده طبقه‌بندی کرد. هدف اصلی آنها **جلوگیری از بارگذاری بیش از حد**، **تضمین استفاده منصفانه** و **حفظ کیفیت خدمات ثابت** در بین همه کلاینت‌ها است.

در دات‌نت، فضای نام System.Threading.RateLimiting چندین استراتژی محدودکننده‌ی داخلی ارائه می‌دهد که هر کدام برای یک مورد استفاده‌ی خاص طراحی شده‌اند. رایج‌ترین انواع مورد استفاده عبارتند از:

1. **محدودکننده نرخ پنجره ثابت** \- محدودکننده مبتنی بر زمان
2. **محدودکننده همزمانی** \- محدودکننده مبتنی بر موازی‌سازی

##### **FixedWindowRateLimiter چیست؟**

FixedWindowRateLimiter یک **مکانیزم محدودکننده نرخ مبتنی بر زمان** است که تعداد درخواست‌هایی را که می‌توانند در یک بازه زمانی مشخص و با مدت زمان ثابت پردازش شوند، تعریف می‌کند، برای مثال، ۱۰۰ درخواست در دقیقه برای هر کاربر یا آدرس IP.

این روش با تقسیم زمان به **فواصل ثابت و غیر همپوشانی**، که به عنوان پنجره شناخته می‌شوند، کار می‌کند. هر پنجره یک شمارنده دارد که نشان می‌دهد تاکنون چند درخواست پردازش شده است.

###### **چگونه کار می‌کند؟**

1. در شروع هر پنجره (مثلاً ۱ دقیقه)، محدودکننده اجازه می‌دهد تا N درخواست (مطابق تعریف‌شده در پیکربندی) ارسال شود.
2. هر درخواست ورودی، شمارنده را افزایش می‌دهد.
3. به محض اینکه شمارنده به حد نصاب برسد (مثلاً ۱۰۰ درخواست)، هرگونه درخواست اضافی در همان بازه زمانی **یا در صف** قرار می‌گیرد (اگر محدودیت صف پیکربندی شده باشد) یا **رد می‌شود.** بلافاصله
4. وقتی پنجره زمانی منقضی می‌شود، شمارنده به صفر بازنشانی می‌شود و پنجره بعدی از نو شروع می‌شود.

###### **قیاس در دنیای واقعی**

یک **گیشه بلیط فروشی سینما را** تصور کنید که فقط ۱۰۰ بلیط در دقیقه می‌فروشد. اگر نفر صد و یکم قبل از پایان آن دقیقه برسد، باید یکی از دو کار زیر را انجام دهد:

- تا دقیقه بعد (پنجره جدید) صبر کنید، یا
- اگر صف پر است، بروید.

این امر بار قابل پیش‌بینی را تضمین می‌کند و از انفجارهای ناگهانی ترافیک که می‌تواند سرویس‌های پایین‌دستی را بیش از حد بارگذاری کند، جلوگیری می‌کند.

**نکته:** ایده‌آل برای **APIهای عمومی**، **کنترل در سطح دروازه** یا **سهمیه‌بندی‌های زمانی یکسان**

##### **محدودکننده همزمانی چیست؟**

ConcurrencyLimiter یک **مکانیزم محدودکننده سرعت مبتنی بر موازی‌سازی** است. به جای محدود کردن درخواست‌ها در هر بازه زمانی، بر روی **تعداد درخواست‌هایی که به طور فعال و همزمان** و به صورت بلادرنگ پردازش می‌شوند، تمرکز می‌کند.

این تعداد ثابتی از مجوزهای همزمان (اسلات‌های فعال) را تعریف می‌کند. وقتی درخواستی می‌رسد، قبل از پردازش باید **مجوزی دریافت کند**. اگر همه مجوزها در حال استفاده باشند، درخواست ورودی:

- در صف منتظر می‌ماند تا یک جایگاه خالی شود، یا
- اگر صف پر باشد، بلافاصله با پاسخ 429 Too Many Requests رد می‌شود.

###### **چگونه کار می‌کند؟**

1. فرض کنید محدودکننده شما اجازه می‌دهد پنج درخواست همزمان ارسال شود.
2. پنج درخواست اول ورودی، مجوز دریافت می‌کنند و بلافاصله پردازش آنها آغاز می‌شود.
3. درخواست ششم متوقف شده و در صف انتظار قرار می‌گیرد.
4. به محض اینکه یکی از ۵ نفر اول کارش را تمام کند، مجوزش را صادر می‌کند.
5. محدودکننده بلافاصله اجازه می‌دهد تا درخواست انتظار بعدی ادامه یابد.

این چرخه ادامه می‌یابد و تضمین می‌کند که سیستم **هرگز بیش از ۵ درخواست را به طور همزمان پردازش نمی‌کند و** عملکرد پایدار را حفظ می‌کند.

###### **قیاس در دنیای واقعی**

را تصور کنید **آسانسوری** که فقط می‌تواند پنج نفر را همزمان در خود جای دهد. اگر 10 نفر منتظر باشند:

- پنج نفر اول پذیرفته می‌شوند (درخواست‌های فعال).
- پنج مورد بعدی منتظر می‌مانند (درخواست‌های در صف).
- وقتی آسانسور برمی‌گردد (درخواست تکمیل می‌شود)، نوبت به نفر دیگری در صف می‌رسد.

این تضمین می‌کند که آسانسور (سیستم) هرگز بار بیشتری از آنچه که می‌تواند به طور ایمن حمل کند، حمل نمی‌کند.

**توجه:** برای **عملیات طولانی مدت**، **پرهزینه** یا **حساس، مانند** پردازش پرداخت یا آپلود داده، ایده‌آل است.

##### **مرحله ۴: ایجاد سرویس سیاست محدودیت نرخ**

**IRateLimitPolicyService** است **رابطی** توسط API Gateway شما را **که نحوه ایجاد و پیکربندی محدودکننده‌های نرخ** بر اساس API مورد دسترسی، بدون کدنویسی منطقی محدودکننده در میان‌افزار، تعریف می‌کند. آن را مانند یک **قرارداد کارخانه‌ای** در نظر بگیرید که محدودکننده‌های نرخ (مثلاً FixedWindow، ConcurrencyLimiter) را طبق قوانین تعریف‌شده در appsettings.json شما تولید می‌کند.

یک رابط با نام **IRateLimitPolicyService.cs** در **پوشه Services** ایجاد کنید، سپس کد زیر را کپی و پیست کنید. این کد یک قرارداد تعریف می‌کند، بنابراین می‌توانید بعداً بدون دست زدن به منطق میان‌افزار، ارائه‌دهنده دیگری (مثلاً مبتنی بر Redis، مبتنی بر پایگاه داده و غیره) را وصل کنید.

```csharp
using APIGateway.Models;
using System.Threading.RateLimiting;

namespace APIGateway.Services
{
    // Defines a contract for creating rate limiters dynamically
    // based on API category (policy) and request identity.
    // The implementing service (RateLimitPolicyService) uses this interface
    // to generate the appropriate RateLimiter instance (FixedWindow, ConcurrencyLimiter, etc.)
    // depending on the policy selected by the middleware.
    public interface IRateLimitPolicyService
    {
        RateLimiter CreateRateLimiter(RateLimitPolicy policy);
    }
}
```

##### **ایجاد سرویس RateLimitPolicy**

RateLimitPolicyService **مغز متفکر و پیکربندی** سیستم محدودکننده نرخ ما است. وظیفه آن این است که:

- **بخوانید،** تنظیمات را از appsettings.json
- **نوع محدودکننده صحیح** (FixedWindow یا Concurrency) را انتخاب کنید.
- **آن را** با محدودیت‌های ما (مانند تعداد درخواست، اندازه صف و غیره) پیکربندی کنید.
- **یک شیء RateLimiter آماده برای استفاده را** به میان‌افزار برمی‌گرداند.

یک فایل کلاس با نام **RateLimitPolicyService.cs** در **پوشه Services** ایجاد کنید، سپس کد زیر را کپی و در آن قرار دهید.

```csharp
using APIGateway.Helpers;
using APIGateway.Models;
using Microsoft.Extensions.Options;
using System.Threading.RateLimiting;

namespace APIGateway.Services
{
    // Responsible for creating and configuring rate limiter instances
    // based on policy definitions found in appsettings.json.
    // Design Goals:
    // • Centralize all limiter creation logic in one place.
    // • Support multiple limiter strategies (FixedWindow, ConcurrencyLimiter, etc.).
    // • Allow global enable/disable toggle via configuration.
    public class RateLimitPolicyService : IRateLimitPolicyService
    {
        // Holds the strongly typed configuration from appsettings.json ("RateLimiting" section).
        private readonly RateLimitSettings _settings;

        // Initializes the policy service using the options pattern to bind configuration.
        // The IOptions<T> abstraction automatically injects RateLimitSettings values from appsettings.json.
        public RateLimitPolicyService(IOptions<RateLimitSettings> options)
        {
            _settings = options.Value;
        }

        // Factory method for creating the appropriate RateLimiter based on the selected policy.
        public RateLimiter CreateRateLimiter(RateLimitPolicy policy)
        {
            // If rate limiting is globally disabled (via appsettings.json),
            // return a lightweight NoopRateLimiter that allows all requests.
            if (!_settings.IsEnabled)
                return new NoRateLimiter();

            // Dynamically choose limiter type based on policy
            return policy switch
            {
                // Product APIs → Use Fixed Window Limiter (e.g., 100 requests per minute)
                RateLimitPolicy.ProductApi => CreateFixedWindowLimiter(_settings.ProductApiPolicy),

                // Order APIs → Also Fixed Window, typically stricter limits than Product
                RateLimitPolicy.OrderApi => CreateFixedWindowLimiter(_settings.OrderApiPolicy),

                // Payment APIs → Use ConcurrencyLimiter (limits simultaneous requests)
                RateLimitPolicy.PaymentApi => CreateConcurrencyLimiter(_settings.PaymentApiPolicy),

                // Fallback to Default Policy for all other APIs
                _ => CreateFixedWindowLimiter(_settings.DefaultPolicy)
            };
        }

        // Creates a FixedWindowRateLimiter based on configuration values.
        // Fixed Window Limiter:
        // Allows up to N requests within a defined "window" duration (e.g., 60/sec, 100/min).
        // Once the window is full, requests are queued or rejected.
        private RateLimiter CreateFixedWindowLimiter(RateLimitSettings.Policy policy)
        {
            return new FixedWindowRateLimiter(new FixedWindowRateLimiterOptions
            {
                // Maximum number of allowed requests in a window (PermitLimit = 100 → 100 req/min)
                PermitLimit = policy.PermitLimit,

                // The time duration defining each window (e.g., "00:01:00" = 1 minute)
                Window = TimeSpan.Parse(policy.Window),

                // Number of extra requests that can be queued after reaching the limit
                QueueLimit = policy.QueueLimit,

                // Defines how queued requests are processed (OldestFirst or NewestFirst)
                QueueProcessingOrder = Enum.Parse<QueueProcessingOrder>(policy.QueueProcessingOrder)
            });
        }

        // Creates a ConcurrencyLimiter based on configuration values.
        // Concurrency Limiter:
        // Restricts the number of concurrent (simultaneous) operations instead of per-minute requests.
        // Ideal for Payment APIs, where only a few payment transactions
        // should be processed at the same time to avoid gateway overload or double submissions.
        private RateLimiter CreateConcurrencyLimiter(RateLimitSettings.Policy policy)
        {
            return new ConcurrencyLimiter(new ConcurrencyLimiterOptions
            {
                // Number of concurrent operations permitted
                PermitLimit = policy.PermitLimit,

                // Additional requests waiting in queue (optional)
                QueueLimit = policy.QueueLimit,

                // Defines how queued requests are processed when slots free up
                QueueProcessingOrder = Enum.Parse<QueueProcessingOrder>(policy.QueueProcessingOrder)
            });
        }
    }
}
```

##### **مرحله ۵: ایجاد میان‌افزار سفارشی**

RateLimitingMiddleware یک **کامپوننت میان‌افزار سفارشی** است که درون خط لوله درخواست HTTP مربوط به API Gateway شما قرار می‌گیرد. وظیفه آن **بررسی هر درخواست ورودی** و تصمیم‌گیری در مورد موارد زیر است:

- **اجازه دهید** (اگر در محدوده نرخ باشد)، یا
- **آن را مسدود کنید** (اگر کلاینت از حد مجاز پیکربندی شده فراتر رفته باشد).

این به عنوان **کنترل‌کننده ترافیک** برای API های شما عمل می‌کند و تضمین می‌کند که هیچ کاربر، آدرس IP یا سیستمی نمی‌تواند میکروسرویس‌های backend شما را تحت الشعاع قرار دهد.

###### **مسئولیت‌های کلیدی**

1. مشخص کنید چه کسی درخواست را انجام می‌دهد (شناسه کاربری از JWT یا آدرس IP).
2. نوع API مورد دسترسی (محصول، سفارش یا پرداخت) را مشخص کنید.
3. بر اساس پیکربندی، قانون محدودکننده نرخ صحیح را اعمال کنید.
4. تعداد درخواست‌های اخیر کاربر/IP را پیگیری کنید.
5. تصمیم بگیرید که آیا درخواست را مجاز یا مسدود کنید.

یک فایل کلاس با نام **RateLimitingMiddleware.cs** در **پوشه Middlewares** ایجاد کنید، سپس کد زیر را کپی و جایگذاری کنید.

```csharp
using APIGateway.Models;
using APIGateway.Services;
using System.Collections.Concurrent;
using System.Security.Claims;
using System.Threading.RateLimiting;

namespace APIGateway.Middlewares
{
    // This middleware enforces rate limiting for every incoming request:
    // For authenticated users → limits are applied per UserId (from JWT).
    // For anonymous users → limits are applied per IP address.
    // Workflow:
    // 1️. Detect which API endpoint is being accessed (Product, Order, Payment, etc.).
    // 2️. Resolve identity (UserId or IP).
    // 3️. Retrieve or create a RateLimiter (based on policy).
    // 4️. Attempt to acquire permission (token) from the limiter.
    // 5️. If denied → return HTTP 429 Too Many Requests.
    // 6️. Otherwise → continue down the pipeline.
    public class RateLimitingMiddleware
    {
        // Points to the next middleware in the pipeline
        private readonly RequestDelegate _next;

        // A dependency that creates the correct RateLimiter
        private readonly IRateLimitPolicyService _policyService;

        // An in-memory thread-safe dictionary that stores a separate limiter per user/IP per policy
        private static readonly ConcurrentDictionary<string, RateLimiter> _limiters = new();

        public RateLimitingMiddleware(RequestDelegate next, IRateLimitPolicyService policyService)
        {
            _next = next;
            _policyService = policyService;
        }

        // This is called automatically by the ASP.NET Core pipeline for every HTTP request.
        public async Task InvokeAsync(HttpContext context)
        {
            // Step 1: Identify the Request Path
            // Extracts the URL path, e.g. /api/products/get-all.
            // Helps the middleware determine which API category the request belongs to.
            var path = context.Request.Path.Value ?? string.Empty;

            // Step 2: Resolve the Request Identity (IP or User Id)
            // This method determines who is making the request.
            var identityKey = ResolveIdentity(context);

            // Step 3: Determine Which API Policy Applies
            // Product, Order, Payment, etc.
            var policy = GetPolicyFromPath(path);

            // Step 4: Combine both to form a unique limiter key
            // Builds a unique key combining policy + user/IP
            // Example: "OrderApi_user:123" or "Default_ip:203.91.45.10"
            var limiterKey = $"{policy}_{identityKey}";

            // Step 5: Retrieve or Create a Limiter
            // Looks up an existing limiter in the dictionary.
            // If not found, creates a new one via RateLimitPolicyService.
            var limiter = _limiters.GetOrAdd(
                limiterKey,
                _ => _policyService.CreateRateLimiter(policy));

            // Step 6: Try to Acquire a Permit
            // This is the actual enforcement line.
            // Requests 1 token(permit) from the limiter.
            // The limiter(either FixedWindow or Concurrency) checks:
            // Has this user already hit their request limit?
            // If not → allow and mark a token as used.
            // If yes → deny access.
            // The lease object tells you if the request was accepted:
            // lease.IsAcquired == true → proceed.
            // lease.IsAcquired == false → reject(too many requests).
            using var lease = await limiter.AcquireAsync(1, context.RequestAborted);

            // Step 6: Handle Rejected Requests
            if (!lease.IsAcquired)
            {
                // Responds with HTTP 429 Too Many Requests.
                context.Response.StatusCode = StatusCodes.Status429TooManyRequests;
                context.Response.ContentType = "application/json";

                // Adds a standard Retry-After header to inform the client when to retry.
                context.Response.Headers["Retry-After"] = "60";

                await context.Response.WriteAsync(
                    "{\"error\":\"rate_limit_exceeded\",\"message\":\"Too many requests. Please try again later.\"}");

                // Stops the request pipeline here — the request doesn’t reach your downstream APIs.
                return;
            }

            // Step 7: Pass Allowed Requests Forward
            // If the limiter allows the request,
            // it’s forwarded to the next middleware or API controller as normal.
            await _next(context);
        }

        // Determines which rate-limiting policy applies based on request path.
        // This ensures different API categories can have different rate limits
        // Example:
        // /api/products → ProductApiPolicy
        // /api/orders → OrderApiPolicy
        // /api/payments → PaymentApiPolicy
        private static RateLimitPolicy GetPolicyFromPath(string path)
        {
            if (path.Contains("/products", StringComparison.OrdinalIgnoreCase))
                return RateLimitPolicy.ProductApi;

            if (path.Contains("/orders", StringComparison.OrdinalIgnoreCase))
                return RateLimitPolicy.OrderApi;

            if (path.Contains("/payments", StringComparison.OrdinalIgnoreCase))
                return RateLimitPolicy.PaymentApi;

            // Default fallback for all other routes
            return RateLimitPolicy.Default;
        }

        // Resolves a unique identity key for the current requester.
        // Priority order:
        // 1️. Authenticated user → Extract UserId from JWT claims.
        // 2️. Anonymous user → Use client IP address (proxy-aware).
        private static string ResolveIdentity(HttpContext context)
        {
            // 1️. Try JWT-based user identification.
            // Looks for claims like NameIdentifier, sub, or userId.
            // If found → identity becomes user: { userId}.
            var userId = context.User?.FindFirst(ClaimTypes.NameIdentifier)?.Value
                      ?? context.User?.FindFirst("sub")?.Value
                      ?? context.User?.FindFirst("userId")?.Value;

            if (!string.IsNullOrWhiteSpace(userId))
                return $"user:{userId}";

            // If no JWT token (anonymous user):
            // Uses IP address as identity key.
            // Checks the X-Forwarded-For header(important when using proxies or CDNs).
            // Example: ip: 203.91.44.88
            var ip = context.Request.Headers["X-Forwarded-For"].FirstOrDefault()
                     ?? context.Connection.RemoteIpAddress?.ToString()
                     ?? "unknown";

            return $"ip:{ip}";
        }
    }
}
```

##### **مرحله 6: افزودن افزونه برای یکپارچه‌سازی تمیز**

این فایل **متدهای افزونه‌ای** ارائه می‌دهد که انجام موارد زیر را آسان می‌کند:

1. **را ثبت کنید، و** سرویس‌های محدودکننده نرخ سفارشی خود (مانند IRateLimitPolicyService و RateLimitSettings)
2. **فعال کنید.** میان‌افزار محدودکننده نرخ (RateLimitingMiddleware) خود را درون خط لوله درخواست

به جای نوشتن کد طولانی مستقیماً در Program.cs، می‌توانید به سادگی فراخوانی کنید:

- builder.Services.AddCustomRateLimiting(configuration);
- محدود کردن نرخ استفاده سفارشی (app.UseCustomRateLimiting();)

متدهای افزونه به شما امکان می‌دهند **منطق راه‌اندازی قابل استفاده مجدد را** به IServiceCollection (برای تزریق وابستگی) و IApplicationBuilder (برای میان‌افزار) اضافه کنید. بنابراین به جای سیم‌کشی دستی سرویس‌ها و میان‌افزار، این متدها مانند موارد زیر عمل می‌کنند: میانبرهای تک‌خطی برای ثبت و فعال‌سازی کل سیستم محدودکننده نرخ شما.

ابتدا، پوشه‌ای به نام Extensions در دایرکتوری ریشه پروژه لایه API Gateway ایجاد کنید. سپس، یک فایل کلاس به نام **RateLimitingExtensions.cs** در **پوشه Extensions** ایجاد کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
using APIGateway.Models;
using APIGateway.Services;
using APIGateway.Middlewares;

namespace APIGateway.Extensions
{
    // Provides extension methods to register and enable
    // custom in-memory rate limiting within the API Gateway.
    public static class RateLimitingExtensions
    {
        // Adds and configures the custom rate limiting services to the dependency injection container.
        public static IServiceCollection AddCustomRateLimiting(
            this IServiceCollection services, IConfiguration configuration)
        {
            // 1️. Bind "RateLimiting" section in appsettings.json → RateLimitSettings model
            // Example:
            // "RateLimiting": {
            //   "IsEnabled": true,
            //   "DefaultPolicy": { ... },
            //   "ProductApiPolicy": { ... }
            // }
            services.Configure<RateLimitSettings>(
                configuration.GetSection("RateLimiting"));

            // 2️. Register the policy service that creates limiters based on configuration
            // This allows the middleware to request a RateLimiter via IRateLimitPolicyService
            services.AddSingleton<IRateLimitPolicyService, RateLimitPolicyService>();

            // Why Singleton?
            // Rate limiting depends on shared in-memory limiters.
            // A singleton ensures consistent throttling across requests.

            // Return for fluent chaining in Program.cs
            return services;
        }

        // Adds the "RateLimitingMiddleware" into the application request pipeline.
        // What this does:
        // Inserts your custom rate-limiting logic before controller execution.
        // Every request will pass through this middleware where it will either:
        // Be allowed → proceed to next middleware or controller, OR
        // Be throttled → immediately return HTTP 429 Too Many Requests.
        // Recommended Placement:
        // Place this middleware early in the pipeline (after authentication but before business logic).
        public static IApplicationBuilder UseCustomRateLimiting(this IApplicationBuilder app)
        {
            // Insert custom middleware into the ASP.NET Core pipeline
            return app.UseMiddleware<RateLimitingMiddleware>();
        }
    }
}
```

##### **مرحله 7: Program.cs**

در یک **ASP.NET Core API Gateway**، فایل Program.cs به عنوان **نقطه ورودی** عمل می‌کند که موارد زیر را ادغام می‌کند:

- Serilog (ثبت وقایع ساختاریافته)
- فشرده‌سازی پاسخ سفارشی

- Swagger برای تست API محلی
- میکروسرویس‌های HttpClients

بنابراین، Program.cs **نقطه ادغام نهایی** شما **است که در آن سیستم محدودکننده نرخ و تنظیم سرعت** درون API Gateway فعال می‌شود. این فایل تضمین می‌کند که:

- محدودکننده نرخ **ثبت شده** است (AddCustomRateLimiting())،
- میان‌افزار **فعال شده** است (UseCustomRateLimiting()) و
- هر دو **مسیر دروازه سفارشی** و **مسیرهای پروکسی Ocelot** قبل از اینکه درخواست‌ها به میکروسرویس‌های backend شما برسند، در برابر استفاده بیش از حد محافظت می‌شوند.

لطفا فایل کلاس Program.cs را به صورت زیر تغییر دهید:

```csharp
using APIGateway.Extensions;
using APIGateway.Middlewares;
using APIGateway.Models;
using APIGateway.Services;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;
using Microsoft.Win32;
using Newtonsoft.Json.Serialization;
using Ocelot.DependencyInjection;
using Ocelot.Middleware;
using Serilog;
using System.Text;

namespace APIGateway
{
    public class Program
    {
        public static async Task Main(string[] args)
        {
            var builder = WebApplication.CreateBuilder(args);

            // MVC Controllers + Newtonsoft JSON Configuration
            builder.Services
                .AddControllers()
                .AddNewtonsoftJson(options =>
                {
                    options.SerializerSettings.ContractResolver = new DefaultContractResolver
                    {
                        NamingStrategy = new DefaultNamingStrategy()
                    };
                });

            // Reads the RateLimiting section from appsettings.json
            // Binds it to your RateLimitSettings model
            // Registers the RateLimitPolicyService as a singleton
            builder.Services.AddCustomRateLimiting(builder.Configuration);

            // Bind CompressionSettings section to our model using options pattern
            builder.Services.Configure<CompressionSettings>(
                builder.Configuration.GetSection("CompressionSettings"));

            // Ocelot Configuration (API Gateway Routing Layer)
            builder.Configuration.AddJsonFile("ocelot.json", optional: false, reloadOnChange: true);
            builder.Services.AddOcelot(builder.Configuration);

            // Structured Logging Setup (Serilog)
            Log.Logger = new LoggerConfiguration()
                .ReadFrom.Configuration(builder.Configuration)
                .Enrich.FromLogContext()
                .CreateLogger();

            builder.Host.UseSerilog(); // Replace default .NET logger with Serilog.

            builder.Services.AddEndpointsApiExplorer();
            builder.Services.AddSwaggerGen();

            // JWT Authentication (Bearer Token Validation)
            builder.Services
                .AddAuthentication(options =>
                {
                    // Define the default authentication scheme as Bearer
                    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
                    options.DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme;
                })
                .AddJwtBearer(options =>
                {
                    // Token validation configuration
                    options.TokenValidationParameters = new TokenValidationParameters
                    {
                        ValidateIssuer = true,
                        ValidIssuer = builder.Configuration["JwtSettings:Issuer"],
                        // We’re not validating audience because microservices share same gateway.
                        ValidateAudience = false,
                        // Enforce token expiry check
                        ValidateLifetime = true,
                        // Ensure token signature integrity using secret key
                        ValidateIssuerSigningKey = true,
                        IssuerSigningKey = new SymmetricSecurityKey(
                            Encoding.UTF8.GetBytes(builder.Configuration["JwtSettings:SecretKey"]!)
                        ),
                        // No extra grace period for expired tokens
                        ClockSkew = TimeSpan.Zero
                    };
                });

            builder.Services.AddAuthorization(); // Enables [Authorize] attributes.

            // Downstream Microservice Clients (typed HttpClientFactory)
            var urls = builder.Configuration.GetSection("ServiceUrls");

            builder.Services.AddHttpClient("OrderService", c =>
            {
                c.BaseAddress = new Uri(urls["OrderService"]!);
            });

            builder.Services.AddHttpClient("UserService", c =>
            {
                c.BaseAddress = new Uri(urls["UserService"]!);
            });

            builder.Services.AddHttpClient("ProductService", c =>
            {
                c.BaseAddress = new Uri(urls["ProductService"]!);
            });

            builder.Services.AddHttpClient("PaymentService", c =>
            {
                c.BaseAddress = new Uri(urls["PaymentService"]!);
            });

            // Custom Aggregation Service Registration
            builder.Services.AddScoped<IOrderSummaryAggregator, OrderSummaryAggregator>();

            var app = builder.Build();

            // Swagger (API Explorer for development/debugging)
            if (app.Environment.IsDevelopment())
            {
                app.UseSwagger();
                app.UseSwaggerUI();
            }

            app.UseHttpsRedirection();

            // Custom conditional compression middleware
            app.UseMiddleware<ConditionalResponseCompressionMiddleware>();

            // Global Cross-Cutting Middleware
            app.UseCorrelationId();
            app.UseRequestResponseLogging();

            // BRANCH 1: Custom Aggregated Endpoints (/gateway/*)
            app.MapWhen(
                ctx => ctx.Request.Path.StartsWithSegments("/gateway", StringComparison.OrdinalIgnoreCase),
                gatewayApp =>
                {
                    // Enable endpoint routing for this sub-pipeline
                    gatewayApp.UseRouting();

                    // Apply authentication & authorization
                    gatewayApp.UseAuthentication();
                    gatewayApp.UseAuthorization();

                    // Apply rate limiting also inside this sub-pipeline if needed
                    gatewayApp.UseCustomRateLimiting();

                    // Register controller actions under this branch
                    gatewayApp.UseEndpoints(endpoints =>
                    {
                        endpoints.MapControllers();
                    });
                });

            // BRANCH 2: Ocelot Reverse Proxy
            app.UseAuthentication();

            // Register rate limiting globally here
            app.UseCustomRateLimiting();

            // Middleware for pre-validation of Bearer tokens (optional)
            app.UseGatewayBearerValidation();

            // Ocelot middleware handles routing, transformation, and load-balancing
            await app.UseOcelot();

            // Start the Application
            app.Run();
        }
    }
}
```

##### **تست محدود کردن نرخ و تنظیم سرعت با استفاده از Postman**

پس از پیاده‌سازی تمام مراحل (میان‌افزار، سرویس‌ها و پیکربندی در appsettings.json)، تأیید خواهید کرد که API Gateway شما به درستی درخواست‌ها را به میکروسرویس‌های مختلف محدود و کنترل می‌کند.

##### **محدودکننده نرخ تست (APIهای محصول/سفارش)**

###### **مرحله ۱: ایجاد درخواست**

1. در Postman، روی **\+ New → HTTP Request** کلیک کنید.
2. (GET یا POST) را انتخاب کنید. **روش** بسته به نقطه پایانی که می‌خواهید آزمایش کنید،
مثال:
3. دریافت https://localhost:7204/products/products?pageNumber=1&pageSize=20
4. یک بار آن را امتحان کنید، و باید پاسخ ۲۰۰ OK دریافت کنید.

###### **مرحله ۲. درخواست را در یک مجموعه ذخیره کنید**

1. کلیک کنید. **روی دکمه ذخیره** (بالا سمت راست درخواست)
2. را انتخاب کنید **گزینه + New Collection** و یک نام برای آن انتخاب کنید، مثلاً Rate Limit Tests.
3. درخواست خود را درون آن مجموعه ذخیره کنید.

###### **مرحله ۳. باز کردن برنامه‌ی Postman Collection Runner**

1. در نوار کناری سمت چپ، **بخش «مجموعه‌ها»** را باز کنید.
2. موس را روی مجموعه خود (Rate Limit Tests) ببرید و روی **دکمه اجرا (Run** ) کلیک کنید (یا راست کلیک کنید و گزینه «اجرای مجموعه» را انتخاب کنید).
3. این **پنجره‌ی Collection Runner** را باز می‌کند.

###### **مرحله ۴. پیکربندی دونده**

در پنجره‌ی دونده:

1. تعداد تکرار: ۱۲۰. یک درخواست را ۱۲۰ بار ارسال می‌کند
2. تأخیر (میلی‌ثانیه). 0. بدون تأخیر بین درخواست‌ها، همه به سرعت اجرا می‌شوند
3. فایل داده. خالی بگذارید. (اینجا لازم نیست)
4. محیط. محیط خود را انتخاب کنید. (اختیاری)

###### **مرحله ۵: اجرای مجموعه**

کلیک کنید **روی اجرای تست‌های محدودیت نرخ**. پستچی شروع به ارسال سریع ۱۲۰ درخواست (با فاصله ۰ میلی‌ثانیه) خواهد کرد.

نتایج را به صورت زنده مشاهده خواهید کرد:

- ۶۰/۱۰۰ درخواست اول → **۲۰۰ مورد تایید**
- بعد از آستانه پیکربندی شده → **۴۲۹ درخواست‌های بیش از حد**

##### **چه زمانی از محدودیت نرخ و تنظیم سرعت استفاده کنیم**

**از محدودیت سرعت و تنظیم سرعت در موارد زیر استفاده کنید:**

- API های شما **به صورت عمومی در معرض** چندین کلاینت قرار دارند.
- شما می‌خواهید **از سوءاستفاده یا استفاده بیش از حد جلوگیری کنید**.
- سیستم شما باید **به طرز ماهرانه‌ای افزایش ترافیک را مدیریت کند**.
- شما می‌خواهید **طرح‌های استفاده مبتنی بر ردیف ارائه دهید**.
- سرویس‌های بک‌اند شما **به منابع حساس هستند.** (مانند APIهای پرداخت، جستجو یا تجزیه و تحلیل)

این مکانیزم‌ها به شما کمک می‌کنند تا ثبات، عملکرد قابل پیش‌بینی و انصاف کاربری را حفظ کنید - حتی زمانی که ترافیک به طور ناگهانی افزایش می‌یابد.

##### **چه زمانی باید از آن اجتناب کرد یا آن را کنار گذاشت**

اگرچه محدود کردن نرخ برای APIهای عمومی ضروری است، اما موقعیت‌هایی وجود دارد که می‌توانید آن را غیرفعال یا غیرفعال کنید:

- برای **ارتباط داخلی** بین میکروسرویس‌های مورد اعتماد. (سرویس‌های درون کلاستر خودتان نباید محدود شوند.)

- وقتی API شما **کارهای دسته‌ای یا کوئری‌های تحلیلی را** ارائه می‌دهد که به طور قانونی نیاز به واکشی حجم زیادی از داده‌ها به طور همزمان دارند.

در این موارد، می‌توانید آن را خاموش کنید یا **محدودیت‌های بالاتری را** برای کاربران یا نقش‌های خاص اعمال کنید.

API Gateway این موارد را به صورت پویا بر اساس نقش‌های کاربر یا کلیدهای API اعمال می‌کند و به شما کنترل انعطاف‌پذیر و مبتنی بر سیاست را می‌دهد.

##### **نتیجه‌گیری**

محدود کردن سرعت و تنظیم سرعت (Throttling) مانند **محافظان امنیتی برای API Gateway شما** هستند. آن‌ها تضمین می‌کنند که هیچ کاربر، برنامه یا اسکریپتی نمی‌تواند درخواست‌های زیادی ارسال کند و سیستم شما را کند کند.

شما **در معماری میکروسرویس‌های تجارت الکترونیک**، آن‌ها از سرویس‌های حیاتی مانند **APIهای محصول**، **سفارش** و **پرداخت** در برابر فراخوانی‌های بیش از حد محافظت می‌کنند و پلتفرم شما را در شرایط عادی و پرترافیک، قابل اعتماد، ایمن و کارآمد نگه می‌دارند.
