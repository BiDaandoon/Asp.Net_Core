## **API Gateway در میکروسرویس‌های ASP.NET Core Web API**

سیستم‌های نرم‌افزاری مدرن به سرعت در حال فاصله گرفتن از **معماری‌های یکپارچه (Monolithic)** به سمت **معماری‌های مبتنی بر میکروسرویس‌ها (Microservices-Based Architectures)** تشکیل شده است **) هستند، که در آن یک برنامه از بسیاری از سرویس‌های کوچک، مستقل و قابل استقرار** . این رویکرد مزایای فوق‌العاده‌ای از نظر **مقیاس‌پذیری، ماژولاریتی و انعطاف‌پذیری** به همراه دارد، اما چالش‌های جدیدی را در **ارتباطات، مسیریابی** و **مدیریت سرویس** نیز ایجاد می‌کند.

در یک **اکوسیستم میکروسرویس**، ده‌ها سرویس ممکن است در **سرورها، کانتینرها یا محیط‌های ابری مختلف** اجرا شوند. هر سرویس می‌تواند **به طور مستقل شروع، متوقف یا مقیاس‌پذیر شود** و باعث شود موقعیت شبکه (IP یا پورت) آن مرتباً تغییر کند. مدیریت ارتباط مستقیم بین کلاینت‌ها و این سرویس‌های پویا پیچیده، مستعد خطا و ناکارآمد می‌شود.

با افزایش تعداد سرویس‌ها، اطمینان از اینکه هر سرویس می‌تواند به طور ایمن و کارآمد، سرویس‌های دیگر را پیدا کرده و با آنها ارتباط برقرار کند، به طور فزاینده‌ای پیچیده می‌شود. اینجاست که **دروازه‌های API** و **مکانیسم‌های کشف سرویس** وارد عمل می‌شوند.

- API **Gateway** به عنوان **نقطه ورود واحد** برای همه **درخواست‌های کلاینت**، **عمل می‌کند و مسیریابی** متعادل‌سازی **بار**، **احراز هویت**، **محدود کردن نرخ**، **ذخیره‌سازی** ثبت وقایع، **موقت** و **تجمیع** بین کلاینت‌های خارجی و میکروسرویس‌های داخلی را مدیریت می‌کند.
- **کشف سرویس** از سوی دیگر، **تضمین می‌کند که سرویس‌ها می‌توانند به صورت پویا، بدون آدرس‌های کدگذاری شده یا پیکربندی‌های دستی، یکدیگر را پیدا کرده و با یکدیگر ارتباط برقرار کنند**. این امر، ارتباط داخلی یکپارچه را حتی در صورت افزایش مقیاس، راه‌اندازی مجدد یا جابجایی سرویس‌ها امکان‌پذیر می‌کند.

این دو مؤلفه در کنار هم، **ستون فقرات ارتباطی** هر سیستم میکروسرویس ASP.NET Core Web API مدرن را تشکیل می‌دهند و روشی یکپارچه، ایمن و پویا برای اتصال سرویس‌ها و ارائه عملکرد قابل اعتماد در محیط‌های توزیع‌شده فراهم می‌کنند.

#### **درگاه API چیست؟**

یک **API Gateway** است **نقطه ورود واحد** برای همه درخواست‌های کلاینت در یک **سیستم مبتنی بر میکروسرویس‌ها**.
به جای اینکه به کلاینت‌ها (مانند برنامه‌های وب یا موبایل یا سیستم‌های همکار) اجازه داده شود تا مستقیماً با چندین سرویس backend ارتباط برقرار کنند، همه درخواست‌ها از طریق **API Gateway** هدایت می‌شوند.

API Gateway به عنوان یک **پروکسی معکوس هوشمند عمل می‌کند.** این دروازه درخواست‌های ورودی کلاینت را دریافت می‌کند، مشخص می‌کند که کدام میکروسرویس (یا میکروسرویس‌ها) باید آنها را مدیریت کند، آنها را بر اساس آن مسیریابی می‌کند و سپس پاسخ ترکیبی را جمع‌آوری کرده و به کلاینت بازمی‌گرداند.

بنابراین، **API Gateway به عنوان پل ارتباطی** بین **کلاینت‌ها** و **میکروسرویس‌های توزیع‌شده** تضمین می‌کند. **عمل می‌کند و امنیت، مقیاس‌پذیری و کارایی عملیاتی را** در معماری میکروسرویس‌های مدرن ASP.NET Core Web API

##### **قیاس بلادرنگ - میز پذیرش یک سازمان هوشمند**

- وقتی وارد یک دفتر بزرگ می‌شوید، در اطراف دنبال بخش منابع انسانی، مالی یا فناوری اطلاعات نمی‌گردید. شما به **میز پذیرش** می‌روید.
- مسئول پذیرش، هویت شما را تأیید می‌کند (احراز هویت)، هدف شما را ارزیابی می‌کند و شما را به بخش مربوطه هدایت می‌کند (مسیریابی).
- درگاه API نیز همین نقش را ایفا می‌کند، نقطه هوشمند واحدی که هر بازدیدکننده (درخواست کلاینت) ورودی به سازمان (سیستم) را مدیریت می‌کند.

#### **چرا درگاه API در میکروسرویس‌ها اهمیت دارد؟**

در معماری میکروسرویس‌ها، کلاینت‌ها اغلب نیاز به تعامل با چندین سرویس مستقل مانند OrderService، ProductService و PaymentService دارند. بدون یک API Gateway، هر کلاینت باید مکان، نسخه و جزئیات امنیتی هر سرویس را بداند که منجر به **ارتباطات پیچیده و تنگاتنگ** می‌شود.

API **Gateway** با عمل کردن به عنوان یک **درگاه ورودی هوشمند و واحد** به کل سیستم میکروسرویس‌ها، این چالش‌ها را حل می‌کند. این درگاه، پیچیدگی داخلی سرویس‌های زیربنایی را پنهان می‌کند و یک رابط یکپارچه برای همه تعاملات کلاینت فراهم می‌کند. دلایل کلیدی زیر، اهمیت وجود یک API Gateway را نشان می‌دهند.

##### **مسیریابی هوشمند**

مسئولیت اصلی یک API Gateway، **هدایت درخواست‌های ورودی کلاینت** به میکروسرویس صحیح backend است. این مسیریابی تضمین می‌کند که درخواست‌ها بدون نیاز کلاینت‌ها به دانستن جزئیات سرویس داخلی، به سرویس صحیح برسند. این API از تکنیک‌های مختلف مسیریابی مانند موارد زیر پشتیبانی می‌کند:

- **مسیریابی مبتنی بر مسیر:** درخواست‌ها را بر اساس مسیر URL مسیریابی می‌کند. مثال: /api/products → ProductService.
- **مسیریابی مبتنی بر هدر یا مبتنی بر متد:** درخواست‌ها را بسته به هدرها یا متدهای HTTP (GET، POST) مسیریابی می‌کند. برای قوانین مسیریابی پویاتر یا مشروط‌تر استفاده می‌شود *.*
- **مسیریابی مبتنی بر نسخه:** ترافیک را به نسخه‌های مختلف API، مانند /v1/orders یا /v2/orders هدایت می‌کند. برای سازگاری با نسخه‌های قبلی هنگام انتشار ویژگی‌های جدید مفید است *.*
- **مسیریابی آبی-سبز یا Canary:** به تدریج بخش کوچکی از ترافیک را به نسخه جدید ارسال می‌کند در حالی که نسخه قدیمی همچنان در حال اجرا است. ریسک را در طول استقرار به حداقل می‌رساند.

این انعطاف‌پذیری به شما امکان می‌دهد تا سرویس‌ها را به‌طور مستقل تکامل دهید، نسخه‌های جدید را با خیال راحت راه‌اندازی کنید و ترافیک را به‌طور کارآمد و بدون ایجاد اختلال در یکپارچه‌سازی کلاینت‌ها مدیریت کنید.

###### **قیاس بلادرنگ: مرکز مرتب‌سازی پستی**

یک **مرکز مرتب‌سازی پستی** را در نظر بگیرید. هر نامه (درخواست مشتری) به یک مرکز واحد (دروازه API) می‌رسد.

- مرتب‌ساز پستی به *آدرس* (مسیر URL) نگاه می‌کند و تصمیم می‌گیرد که به کدام شهر (میکروسرویس) برود.
- گاهی اوقات، نامه‌ها مهر «اولویت» یا «ثبت‌شده» (مسیریابی مبتنی بر سرآیند) دریافت می‌کنند.
- کدهای پستی قدیمی و جدید (نسخه‌های API) ممکن است در طول انتقال‌ها همزمان وجود داشته باشند.

این منطق مرکز مرتب‌سازی تضمین می‌کند که هر بسته بدون اینکه فرستنده از مسیرهای داخلی پیچیده مطلع شود، به مقصد صحیح خود برسد.

##### **تجمیع و ترکیب**

برنامه‌های مدرن اغلب **نیاز به واکشی داده‌ها از چندین میکروسرویس** برای ارائه یک درخواست کلاینت واحد، دارند. API Gateway می‌تواند **جمع‌آوری** یا **ترکیب کند** این پاسخ‌ها را در یک payload یکپارچه. این فرآیند، فراخوانی‌های متعدد شبکه را در یک فراخوانی کاهش می‌دهد و عملکرد کلاینت و تجربه کاربری را بهبود می‌بخشد.

**مثال:**
یک نقطه پایانی «داشبورد مشتری» در Gateway ممکن است:

- دریافت **جزئیات کاربر** از UserService
- دریافت **سفارشات اخیر** از OrderService
- دریافت **وضعیت پرداخت** از PaymentService

سپس آنها را در یک پاسخ JSON واحد ترکیب کنید و همه چیز را در یک فراخوانی API واحد به کلاینت برگردانید. این رویکرد عملکرد را بهبود می‌بخشد، بار سرور را کاهش می‌دهد و منطق سمت کلاینت را ساده می‌کند. کلاینت تمام داده‌های لازم را با یک فراخوانی API واحد دریافت می‌کند.

###### **قیاس در زمان واقعی - پیشخدمت رستوران و کارکنان آشپزخانه**

به جای سفارش دال، سبزی، روتی، رایتا و دسر **یکی یکی** دریافت می‌کنید **، یک تالی** : یک بشقاب که همه چیز برای شما آماده شده است. نقاط پایانی «داشبورد» گیت‌وی نیز همین کار را انجام می‌دهند : **یک درخواست،** جمع‌آوری می‌کند **اطلاعات کاربر + سفارش‌ها + پرداخت‌ها** را از چندین آشپزخانه (سرویس‌ها) **و یک غذای واحد** (JSON یکپارچه) سرو می‌کند.

##### **احراز هویت و مجوز**

API Gateway به عنوان **دروازه امنیتی** اکوسیستم میکروسرویس‌های شما عمل می‌کند. این دروازه تضمین می‌کند که فقط کاربران معتبر، احراز هویت شده و مجاز می‌توانند به سرویس‌های backend دسترسی داشته باشند. این **دروازه، توکن‌های JWT**، **اعتبارنامه‌های OAuth2** یا **کلیدهای API** را اعتبارسنجی می‌کند و **کنترل‌های دسترسی مبتنی بر نقش (RBAC)** را اعمال می‌کند.

- **توکن‌های JWT (توکن‌های وب JSON):** توکن‌های امن و دارای امضای دیجیتالی که هویت و ادعاهای کاربر را قبل از رسیدن درخواست‌ها به سرویس‌های backend تأیید می‌کنند.
- **اعتبارنامه‌های OAuth2:** یک چارچوب مجوزدهی استاندارد که به برنامه‌های شخص ثالث اجازه می‌دهد بدون به اشتراک گذاشتن رمزهای عبور، به داده‌های کاربر به صورت ایمن دسترسی پیدا کنند.
- **کلیدهای API:** شناسه‌های منحصر به فردی که برای اعتبارسنجی استفاده مشروع از API به هر کلاینت یا سرویس داده می‌شود.
- **کنترل دسترسی مبتنی بر نقش (RBAC):** دسترسی را بر اساس نقش‌های تعیین‌شده برای کاربران (مثلاً مدیر، مدیر، کاربر) محدود می‌کند و تضمین می‌کند که هر کاربر فقط می‌تواند اقدامات مجاز را انجام دهد.

با اعتبارسنجی این اعتبارنامه‌ها در Gateway، هر درخواستی که وارد سیستم می‌شود، از قبل تأیید و ایمن شده است. این اعتبارسنجی متمرکز، اجرای امنیت منسجم را تضمین می‌کند و نیاز به اینکه هر میکروسرویس منطق احراز هویت را به طور مستقل مدیریت کند، از بین می‌برد.

###### **قیاس بلادرنگ – نگهبان کلوپ شبانه با سطوح دسترسی مختلف**

API Gateway **، دروازه‌بان امنیتی** است که اعتبارنامه‌ها را قبل از رسیدن درخواست‌ها به سرویس‌های داخلی، اعتبارسنجی می‌کند.

- **توکن JWT → مهر دیجیتال:** ثابت می‌کند که شما پرداخت کرده‌اید و می‌توانید وارد شوید.
- **OAuth2 → VIP Pass:** به برنامه‌های همکار اجازه می‌دهد بدون به اشتراک گذاشتن رمز عبور شما، از طرف شما وارد شوند.
- **کلید API → رمز عبور مهمان:** مشخص می‌کند کدام مهمان (برنامه) داخل است.
- **RBAC → مناطق دسترسی:** فقط مدیران می‌توانند وارد اتاق VIP (بخش مدیریت) شوند.

درست همانطور که مامور نگهبانی قبل از اجازه ورود افراد، کارت شناسایی و مجوز ورود آنها را بررسی می‌کند، دروازه (Gateway) نیز برای حفظ امنیت سیستم، هر درخواست را تأیید می‌کند.

##### **محدود کردن نرخ و تنظیم سرعت**

برای جلوگیری از استفاده بیش از حد یا حملات مخرب، API Gateway **تعداد درخواست‌هایی** (محدود کردن سرعت و کاهش سرعت) که هر کاربر یا سرویس می‌تواند در یک بازه زمانی مشخص انجام دهد را کنترل می‌کند.

###### **چرا:**

- **سوءاستفاده:** زمانی که یک کاربر یا اسکریپت به طور مکرر (عمدی یا تصادفی) یک API را برای بهره‌برداری از منابع فراخوانی می‌کند.
- **حملات انکار سرویس (DoS):** ارسال سیل‌آسای درخواست‌ها به API برای از دسترس خارج کردن یا کند کردن آن برای کاربران واقعی.
- **افزایش ناگهانی ترافیک:** افزایش غیرمنتظره ترافیک قانونی، مثلاً در زمان فروش ویژه یا راه‌اندازی اپلیکیشن.

###### **انواع کنترل:**

- **محدودیت‌های سرعت:** تعداد درخواست‌های مجاز در هر بازه زمانی (مثلاً ۱۰۰ درخواست در دقیقه) را تعریف کنید.
- **سهمیه‌ها:** کل استفاده را در دوره‌های طولانی‌تر (مثلاً ۱۰۰۰۰ درخواست در روز) تعریف کنید.

###### **گزینه‌های محدوده‌بندی:**

- **به ازای هر کلاینت:** محدودیت‌های اعمال‌شده برای هر کاربر یا برنامه.
- **به ازای هر مسیر:** محدودیت‌های اعمال‌شده برای نقاط انتهایی خاص (مثلاً /api/orders).

با اعمال این کنترل‌ها، API Gateway استفاده منصفانه را تضمین می‌کند، از خرابی جلوگیری می‌کند و منابع backend را از اضافه بار محافظت می‌کند.

###### **قیاس بلادرنگ - گیت عوارضی بزرگراه** .

- ورود همزمان تعداد زیادی ماشین (درخواست) می‌تواند بزرگراه (بخش انتهایی بزرگراه) را مسدود کند.
- دکه‌های عوارضی (محدودکننده‌های نرخ) تعداد خودروهای عبوری در دقیقه را کنترل می‌کنند.
- خطوط VIP (به ازای هر کلاینت) یا مسیرهای ویژه (به ازای هر نقطه پایانی) محدودیت‌های سفارشی دارند.
- سهمیه‌های ترافیک روزانه، تعادل بلندمدت را تضمین می‌کنند.

این امر باعث می‌شود ترافیک روان باشد و از مسدود کردن دیگران توسط رانندگان بی‌احتیاط (سوءاستفاده‌کنندگان) جلوگیری کند.

##### **متعادل‌سازی بار**

متعادل‌سازی بار، API Gateway را قادر می‌سازد تا ترافیک ورودی را به طور مساوی بین چندین نمونه سرویس توزیع کند، عملکرد را افزایش دهد و از بارگذاری بیش از حد هر نمونه واحد جلوگیری کند. همچنین **بررسی‌های سلامت را** انجام می‌دهد تا اطمینان حاصل شود که درخواست‌ها فقط به نمونه‌های سالم ارسال می‌شوند و در نتیجه، دسترسی‌پذیری و قابلیت اطمینان را بهبود می‌بخشد.

از هر یک از الگوریتم‌های زیر برای توزیع ترافیک استفاده می‌کند.

- **الگوریتم راند-رابین (Round-Robin):** به طور متوالی هر درخواست جدید را به نمونه بعدی در لیست، ساده و منصفانه، هدایت می‌کند.
- **کمترین اتصالات:** درخواست‌ها را به نمونه‌ای با کمترین اتصالات فعال ارسال می‌کند - عالی برای حجم کاری ناهموار.
- **مسیریابی مبتنی بر هش:** از هشینگ سازگار (مثلاً بر اساس شناسه کاربر، شناسه کلاینت یا IP) استفاده می‌کند تا اطمینان حاصل شود که درخواست‌های یک کلاینت همیشه به یک نمونه می‌رسند.

این امر، دسترسی‌پذیری بالا، تحمل‌پذیری خطا و استفاده بهینه از منابع را در سراسر میکروسرویس‌های توزیع‌شده تضمین می‌کند.

###### **آنالوگ بلادرنگ – مدیر صف مرکز تماس**

وقتی تماس‌گیرندگان با پشتیبانی تماس می‌گیرند، یک IVR آنها را به **اپراتور بعدی** که اغلب **کم‌مشغله‌تر است** هدایت می‌کند یا **VIPها را به یک میز اختصاصی پین می‌کند** (نمونه‌ها) استفاده می‌کند **. این درگاه از سیاست‌های نوبت‌دهی چرخشی**، **حداقل اتصالات** یا **مبتنی بر هش** برای توزیع یکنواخت تماس‌ها و اطمینان از ارسال آنها به **سالم** اپراتورهای

##### **ذخیره‌سازی و فشرده‌سازی**

برای بهبود سرعت و کاهش حجم کار backend، API Gateway می‌تواند پاسخ‌ها را ذخیره (cache) کرده و قبل از ارسال به کلاینت، آنها را فشرده کند. این API از ویژگی‌هایی مانند **Per-Route Caching**، **ETags**، **Conditional Requests** و **GZIP/Brotli Compression** پشتیبانی می‌کند که زمان پاسخ سریع‌تر و کارایی بهتر شبکه را ممکن می‌سازد.

- **ذخیره‌سازی بر اساس مسیر:** قوانین ذخیره‌سازی را روی مسیرهای خاص اعمال می‌کند (مثلاً، cache /api/products اما نه /api/orders).
- **ETagها (برچسب‌های موجودیت):** برچسب‌های موجودیت (شناسه‌ها) برای اعتبارسنجی اینکه آیا داده‌های ذخیره‌شده هنوز تازه هستند یا نیاز به به‌روزرسانی دارند، استفاده می‌شوند.
- **درخواست‌های شرطی:** به کلاینت‌ها اجازه می‌دهد فقط در صورتی از داده‌های ذخیره‌شده در حافظه پنهان استفاده کنند که هنوز معتبر باشند و ترافیک غیرضروری شبکه را کاهش می‌دهد. این بدان معناست که به کلاینت اجازه می‌دهد فقط در صورتی داده‌ها را دریافت کند که از آخرین درخواست تغییر کرده باشند.
- **فشرده‌سازی GZIP/Brotli:** فایل‌های پاسخ را قبل از انتقال فشرده می‌کند تا پهنای باند را به حداقل برساند و زمان بارگذاری را بهبود بخشد.

ذخیره‌سازی موقت، داده‌هایی را که مرتباً درخواست می‌شوند، ذخیره می‌کند تا درخواست‌های مکرر بتوانند به سرعت و بدون نیاز به بارگذاری مجدد در هر بار، ارائه شوند. این کار بار سرور را کاهش داده و زمان پاسخگویی را بهبود می‌بخشد، در حالی که فشرده‌سازی، تحویل سریع‌تر داده‌ها را در شبکه‌های کندتر تضمین می‌کند.

###### **قیاس بلادرنگ – کتابدار کتابخانه و دستگاه فتوکپی**

یک کتابدار (API Gateway) کتاب‌های محبوب (پاسخ‌های ذخیره‌شده) را برای دسترسی سریع، به جای اینکه هر بار از حافظه‌ی ذخیره‌سازی بیرون بکشد، روی میز پذیرش نگه می‌دارد.

##### **تبدیل درخواست و پاسخ**

API Gateway می‌تواند هم **درخواست‌های ورودی و هم پاسخ‌های خروجی را** تغییر دهد تا سازگاری بین کلاینت‌ها و سرویس‌های backend تضمین شود.

###### **نمونه‌هایی از تبدیل‌ها:**

- تغییر یا تغییر نام هدرها و پارامترها.
- بازنویسی URLها برای مطابقت با نقاط پایانی سرویس به‌روزرسانی‌شده.
- تغییر نام فیلدهای JSON یا تغییر ساختار اشیاء.
- تنظیم پاسخ‌ها برای انواع مختلف دستگاه (وب، موبایل، اینترنت اشیا).

تحول، کلاینت‌ها را از تغییرات بک‌اند جدا می‌کند و به سرویس‌ها اجازه می‌دهد بدون ایجاد اختلال در برنامه‌های کلاینت، تکامل یابند.

###### **قیاس بلادرنگ – مترجم زبان در یک کنفرانس**

- گویندگان (میکروسرویس‌ها) ممکن است از زبان‌های مختلفی استفاده کنند؛ مترجم (API Gateway) پیام‌ها را تبدیل می‌کند تا مخاطبان (مشتریان) بتوانند آنها را به وضوح درک کنند.
- حتی اگر گوینده واژگان خود را تغییر دهد (مثلاً نسخه را ارتقا دهد)، مترجم بدون ایجاد وقفه در مکالمه، آن را متناسب با آن تنظیم می‌کند.

##### **قابلیت مشاهده و نظارت (ثبت وقایع)**

API Gateway به عنوان نقطه مشاهده مرکزی برای **نظارت بر ترافیک، عملکرد و سلامت سیستم** عمل می‌کند. این قابلیت‌ها به تیم‌ها کمک می‌کنند تا مشکلات را به موقع تشخیص دهند، وابستگی‌ها را درک کنند و سطح بالایی از قابلیت اطمینان سرویس را حفظ کنند.

###### **عناصر اصلی مشاهده‌پذیری:**

- **گزارش‌ها:** جزئیات درخواست‌ها و پاسخ‌ها را برای اشکال‌زدایی و حسابرسی ثبت می‌کند.
- **ردیابی‌ها:** مسیر یک درخواست را در چندین سرویس ردیابی کنید تا گلوگاه‌ها را شناسایی کنید.
- **شناسه‌های همبستگی:** شناسه‌های منحصر به فردی که به هر درخواست اضافه می‌شوند تا لاگ‌ها و ردیابی‌های مرتبط را به هم متصل کنند.

###### **قیاس بلادرنگ – رادار کنترل ترافیک هوایی**

- هر هواپیمایی (درخواست) که وارد حریم هوایی می‌شود، با رادار (ثبت وقایع و اندازه‌گیری‌ها) رصد می‌شود. کنترل‌کننده به هر هواپیما یک شماره پرواز منحصر به فرد (شناسه همبستگی) اختصاص می‌دهد تا کل سفر آن را ردیابی کند (ردیابی).
- اگر یک هواپیما تأخیر داشته باشد، برج مراقبت (API Gateway) فوراً سایر هواپیماها را شناسایی و برای جلوگیری از برخورد (از کارافتادگی) برنامه‌ریزی مجدد می‌کند.

#### **پیاده‌سازی‌های محبوب API Gateway در اکوسیستم ASP.NET Core**

در اکوسیستم ASP.NET Core، چندین **راهکار API Gateway** به مدیریت مسیریابی، امنیت، متعادل‌سازی بار و تجمیع سرویس بین کلاینت‌ها و میکروسرویس‌ها کمک می‌کنند. هر ابزار از نظر انعطاف‌پذیری، عملکرد و عمق ادغام متفاوت است و به معماران اجازه می‌دهد ابزاری را انتخاب کنند که به بهترین وجه با مقیاس و الزامات سیستم آنها مطابقت داشته باشد. موارد زیر محبوب‌ترین پیاده‌سازی‌های API Gateway مورد استفاده در استقرارهای میکروسرویس‌های .NET در دنیای واقعی هستند:

##### **Ocelot – درگاه سبک و بومی دات‌نت**

Ocelot یک **API Gateway متن‌باز و مبتنی بر جامعه** است که به‌طور خاص برای .NET Core طراحی شده است. این API سبک، پیکربندی آن آسان و برای **سیستم‌های میکروسرویس کوچک تا متوسط** ​​ایده‌آل است.

###### **نکات برجسته کلیدی:**

- کاملاً با .NET نوشته شده و به صورت چندسکویی اجرا می‌شود.
- از یک فایل پیکربندی ساده مبتنی بر JSON (ocelot.json) استفاده می‌کند.
- پشتیبانی می‌کند **از مسیریابی، احراز هویت، محدود کردن سرعت، متعادل‌سازی بار، ذخیره‌سازی موقت، سیاست‌های QoS و تجمیع درخواست**.
- با **Consul، Eureka و IdentityServer ادغام می‌شود.** برای کشف سرویس و امنیت،
- انتخابی عالی برای توسعه‌دهندگانی که راه‌حل‌های میکروسرویس بومی ASP.NET Core می‌سازند.

**بهترین برای:** پروژه‌هایی که به یک **درگاه سبک، خود-میزبان و سازگار با دات‌نت** با حداقل تنظیمات نیاز دارند.

##### **YARP (یکی دیگر از پروکسی‌های معکوس) – دروازه‌ی با کارایی بالای مایکروسافت**

توسعه و نگهداری می‌شود **YARP که توسط مایکروسافت**، یک **کتابخانه پروکسی معکوس مدرن و با کارایی بالا** است که بر روی خط لوله میان‌افزار ASP.NET Core ساخته شده است. این کتابخانه بسیار توسعه‌پذیر است و به توسعه‌دهندگان کنترل کامل بر مسیریابی، سیاست‌ها و تنظیم عملکرد را می‌دهد.

###### **نکات برجسته کلیدی:**

- ادغام عمیق با مدل میزبانی و میان‌افزار ASP.NET Core.
- پشتیبانی می‌کند **از بارگذاری مجدد پیکربندی پویا**، **به‌روزرسانی‌های مسیریابی فوری** و **استراتژی‌های متعادل‌سازی بار سفارشی**.
- ایده‌آل برای سناریوهایی که توسعه‌دهندگان نیاز دارند منطق پروکسی را مستقیماً در برنامه‌های ASP.NET Core موجود جاسازی کنند.
- طراحی شده برای **توان عملیاتی بالا**، **تأخیر کم** و **کنترل کامل** بر روی خطوط لوله درخواست.

**بهترین برای:** سیستم‌های بزرگ یا حساس به عملکرد که نیاز به **ادغام دقیق با ASP.NET Core** و سفارشی‌سازی پیشرفته از طریق کد C# دارند.

##### **Kong Gateway – راهکاری در سطح سازمانی و مستقل از پلتفرم**

Kong یک **API Gateway متن‌باز و مستقل از زبان‌های برنامه‌نویسی** است که بر پایه NGINX ساخته شده و با زبان Lua نوشته شده است. این ابزار به طور گسترده در محیط‌های سازمانی برای مدیریت اکوسیستم‌های میکروسرویس پیچیده و پرترافیک مورد استفاده قرار می‌گیرد.

###### **نکات برجسته کلیدی:**

- غنی **اکوسیستم** از افزونه‌ها برای احراز هویت، تجزیه و تحلیل، محدود کردن نرخ و قابلیت مشاهده.
- پشتیبانی می‌کند **از یکپارچه‌سازی‌های مش سرویس**، **gRPC** و **مسیریابی چند پروتکلی**.
- هر دو **نسخه متن‌باز** و **سازمانی را** با داشبوردها و سیاست‌های امنیتی پیشرفته ارائه می‌دهد.
- مستقل از .NET اجرا می‌شود اما از طریق نقاط پایانی REST یا gRPC به راحتی با میکروسرویس‌های ASP.NET Core ادغام می‌شود.

**بهترین برای:** شرکت‌هایی که **به قابلیت همکاری چندزبانه**، **توسعه‌پذیری مبتنی بر افزونه** و **مقیاس‌پذیری در سطح تولید** نیاز دارند.

##### **سایر دروازه‌های رایج در محیط‌های .NET**

در حالی که Ocelot، YARP و Kong محبوب‌ترین‌ها در اکوسیستم .NET هستند، توسعه‌دهندگان از ابزارهای دیگری نیز بر اساس نیازهای استقرار و مقیاس‌پذیری خود استفاده می‌کنند:

- **NGINX / Envoy / Traefik:** برای پیاده‌سازی‌های کانتینری و مبتنی بر Kubernetes محبوب است؛ تعادل بار قوی و قابلیت مشاهده را ارائه می‌دهد.
- **مدیریت API آژور / دروازه API AWS / Apigee:** دروازه‌های ابری مدیریت‌شده که مقیاس‌پذیری جهانی، سیاست‌های سازمانی و پورتال‌های توسعه‌دهنده یکپارچه را ارائه می‌دهند.

این موارد زمانی ترجیح داده می‌شوند که تیم‌ها به دنبال **راه‌حل‌های مدیریت‌شده توسط ابر**، **مسیریابی چند منطقه‌ای** یا **مدیریت در سطح سازمانی** باشند.

##### **قیاس در زمان واقعی: انتخاب دروازه مناسب مانند انتخاب نقطه ورود مناسب به بزرگراه است**

تصور کنید چندین مسیر به یک شهر (اکوسیستم میکروسرویس شما) منتهی می‌شوند.

- **آسلات** مانند یک دروازه عوارضی ساده و کارآمد برای شهرهای کوچک است، مدیریت آن آسان و راه‌اندازی آن سریع است.
- **YARP** یک تقاطع بزرگراهی مدرن و هوشمند است که برای ترافیک سنگین ساخته شده، انعطاف‌پذیر است و کاملاً با سیستم‌های کنترل محلی یکپارچه شده است.
- **کنگ** قطب بزرگراه جهانی است که از خطوط بین‌المللی، سیستم‌های عوارض چندگانه و هماهنگی در سطح سازمانی پشتیبانی می‌کند.

انتخاب درگاه مناسب، تضمین می‌کند که «ترافیک» شما، درخواست‌های کلاینت، به طور روان، ایمن و کارآمد به دنیای میکروسرویس‌های شما منتقل شود.

##### **آیا همه میکروسرویس‌ها به یک دامنه جداگانه نیاز دارند؟**

**خیر**، هر میکروسرویس **ندارد.** به دامنه عمومی مخصوص به خود نیاز

- در بیشتر محیط‌های عملیاتی، **میکروسرویس‌ها سرویس‌های داخلی هستند**. آن‌ها **پشت دروازه API** قرار دارند و **مستقیماً در معرض اینترنت نیستند**.
- درگاه **API** یک **نقطه ورود عمومی واحد (دامنه) را** در معرض نمایش قرار می‌دهد و درخواست‌ها را به صورت داخلی به میکروسرویس‌های مختلف هدایت می‌کند.

##### **مثال:**

**کلاینت → https://api.mycompany.com (عمومی)**

**↓**

**├── خدمات محصول → https://products-service:5001**

**├── سفارش خدمات → https://orders-service:5002**

**└── خدمات پرداخت → https://payments-service:5003**

در اینجا، همه میکروسرویس‌های داخلی دارای **URLهای داخلی خصوصی** (یا نام‌های DNS کانتینر) هستند، نه دامنه‌های عمومی.

##### **URL های داخلی خصوصی چیستند؟**

**URL های داخلی خصوصی** به **آدرس های شبکه (URL) اشاره دارند که برای ارتباط بین اجزای داخلی** یک سیستم، مانند میکروسرویس ها، پایگاه های داده یا سیستم های backend **که در معرض اینترنت عمومی نیستند،** استفاده می شوند. قابل دسترسی هستند **این URL ها فقط در یک شبکه خصوصی**، مانند:

- یک دستگاه توسعه محلی (مثلاً http://localhost:5001)
- اینترانت یک شرکت (مثلاً http://orderservice.internal.local)
- یک VPC ابری یا شبکه هماهنگ‌کننده کانتینر (مثلاً http://productservice.default.svc.cluster.local در Kubernetes)

###### **ویژگی‌های کلیدی**

- آنها **فقط در داخل شبکه داخلی وجود دارند** (مثلاً http://orderservice:5002 یا http://10.0.1.5:5002).
- آنها **از طریق DNS در معرض اینترنت عمومی قرار نمی‌گیرند**.
- آنها **فقط توسط API Gateway** یا سایر سرویس‌ها برای **ارتباطات داخلی** استفاده می‌شوند.
- آنها **گواهینامه SSL یا IP عمومی ندارند** مدیریت می‌شوند **، زیرا امنیت و SSL در لایه API Gateway**.
- معمولاً **با یکدیگر ارتباط برقرار می‌کنند ، نه از طریق نام دامنه.** میکروسرویس‌ها از طریق این آدرس‌های داخلی

##### **آیا API Gateway به دامنه مخصوص به خود نیاز دارد؟**

**بله.** API Gateway باید یک دامنه عمومی اصلی داشته باشد. **دامنه API Gateway** عمل می‌کند. **به عنوان درب ورودی (Front Door)** برای کل سیستم شما

برای مثال:

- https://api.mycompany.com

پشت صحنه:

- /محصولات → خدمات محصول
- /orders → OrderService
- /پرداخت‌ها → خدمات پرداخت

تمام ترافیک از طریق این دامنه جریان می‌یابد. این جایی است که شما:

- اعمال گواهینامه‌های SSL/TLS
- اجرای احراز هویت/مجوز
- پیاده‌سازی محدودیت نرخ، ذخیره‌سازی موقت و ثبت درخواست‌ها
- نظارت و پیگیری کلیه درخواست‌ها به صورت مرکزی

##### **قیاس بلادرنگ - شماره‌های داخلی خصوصی در یک دفتر**

به میکروسرویس‌های خود مانند کارمندان یک شرکت فکر کنید:

- هر کارمند یک **شماره داخلی خصوصی (مثلاً ۱۰۱** **یا ۱۰۲)** دارد که فقط در داخل شبکه اداری قابل دسترسی است.
- افراد خارجی نمی‌توانند مستقیماً با داخلی‌ها تماس بگیرند؛ آنها **شماره اصلی شرکت را** می‌گیرند و از **منشی** (درگاه API) می‌خواهند که آنها را متصل کند.

به طور مشابه:

- هر میکروسرویس یک **آدرس اینترنتی داخلی خصوصی (Private Internal URL)** دارد.
- کلاینت‌های خارجی از طریق **دامنه اصلی (API Gateway)** متصل می‌شوند.
- دروازه (Gateway) درخواست‌ها را با استفاده از آن URLهای خصوصی به صورت داخلی ارسال می‌کند.

**به طور خلاصه،** URL های داخلی خصوصی، آدرس‌های غیرعمومی هستند که توسط میکروسرویس‌ها برای برقراری ارتباط در یک شبکه داخلی امن استفاده می‌شوند و **API Gateway** تنها مؤلفه‌ای است که یک *دامنه عمومی* را در معرض دنیای خارج قرار می‌دهد.
