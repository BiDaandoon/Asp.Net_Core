
## **OData در میکروسرویس‌های ASP.NET Core Web API**

در این پست، ما در مورد **نحوه پیاده‌سازی OData در ASP.NET Core Web API** بحث خواهیم کرد . در سیستم‌های مدرن مبتنی بر میکروسرویس، APIها توسط رابط‌های کاربری بسیار پویا مانند **داشبوردهای مدیریتی، شبکه‌های کاتالوگ، صفحات گزارش‌دهی و نمایش‌های تحلیلی** استفاده می‌شوند . این رابط‌های کاربری به الگوهای دسترسی به داده‌های انعطاف‌پذیر مانند فیلتر کردن، مرتب‌سازی، صفحه‌بندی، انتخاب ستون و تجمیع نیاز دارند که اغلب توسط تعاملات کاربر هدایت می‌شوند تا قراردادهای API از پیش تعریف‌شده.

به طور سنتی، پشتیبانی از چنین الزاماتی منجر به **انفجار نقطه پایانی** می‌شود : چندین API برای هر ترکیب فیلتر، ترتیب مرتب‌سازی یا تغییر صفحه نمایش. **OData (پروتکل داده باز)** حل می‌کند **این مشکل را با اجازه دادن به کلاینت‌ها برای شکل‌دهی داده‌های مورد نیاز خود از طریق گزینه‌های استاندارد پرس‌وجو** ، در حالی که سرور همچنان کنترل اعتبارسنجی، عملکرد و امنیت را در دست دارد.

#### **سناریوی دنیای واقعی: جدول کاتالوگ محصولات مدیریتی**

پیاده‌سازی خواهیم کرد . این شبکه معمولاً از موارد زیر پشتیبانی می‌کند: **اکنون، ما OData را برای پشتیبانی از یک شبکه کاتالوگ محصولات مدیریتی** ، مشابه آنچه در سیستم‌های تولیدی واقعی مانند پنل‌های مدیریت تجارت الکترونیک می‌بینیم،

- جستجو و فیلتر کردن محصولات (فعال، موجود در انبار، دسته‌بندی)
- مرتب‌سازی بر اساس قیمت، تاریخ ایجاد، موجودی یا رتبه‌بندی
- صفحه‌بندی کارآمد مجموعه داده‌های بزرگ
- انتخاب فقط ستون‌های مورد نیاز برای رابط کاربری
- گسترش داده‌های مرتبط، مانند تصاویر محصول
- نمایش تعداد کل رکوردها برای کنترل‌های صفحه‌بندی

به جای ساخت APIهای جداگانه برای هر یک از این موارد استفاده، ما **یک نقطه پایانی OData واحد را** ارائه خواهیم داد که از همه آنها از طریق گزینه‌های پرس‌وجوی مبتنی بر URL پشتیبانی می‌کند. بیایید این کار را گام به گام در میکروسرویس محصول خود پیاده‌سازی کنیم.

#### **مرحله ۱: نصب بسته OData NuGet (ProductService.API)**

ASP.NET Core به طور پیش‌فرض از OData پشتیبانی نمی‌کند. **بسته Microsoft.AspNetCore.OData** موارد زیر را ارائه می‌دهد:

- **موتور مسیریابی OData:** این API را قادر می‌سازد تا URLهای به سبک OData (مانند $filter، $select و $orderby) را به اکشن‌های کنترلر مربوطه نگاشت کند.
- **تجزیه و اعتبارسنجی پرس‌وجو:** گزینه‌های پرس‌وجوی OData مانند $filter، $select، $orderby، $top و غیره را می‌خواند و آنها را اعتبارسنجی می‌کند تا از پرس‌وجوهای نامعتبر یا ناامن جلوگیری کند.
- **پشتیبانی از EDM (مدل داده موجودیت):** این پشتیبانی یک مدل ابرداده EDM می‌سازد که موجودیت‌ها و روابط API ما را توصیف می‌کند، بنابراین OData می‌داند چه چیزی را می‌توان جستجو کرد و چگونه.
- **ترجمه کوئری‌های OData به عبارات LINQ:** این گزینه، گزینه‌های کوئری OData را به LINQ تبدیل می‌کند، بنابراین کوئری پایگاه داده ما (از طریق EF Core یا IQueryable) بر اساس درخواست، به طور کارآمد اجرا می‌شود.

#### **مرحله 2: نمایش IQueryable در سطح مخزن**

وقتی با یک API معمولی کار می‌کنیم، معمولاً نقاط پایانی ثابتی مانند زیر می‌نویسیم:

- دریافت همه محصولات
- محصولات فعال دریافت کنید
- دریافت محصولات بر اساس دسته بندی
- محصولات پرفروش را دریافت کنید

اما در برنامه‌های واقعی (به‌ویژه یک **جدول محصولات مدیریتی** )، رابط کاربری بسته به کاری که مدیر انجام می‌دهد، پرس‌وجو را تغییر می‌دهد:

- کادر جستجو → فیلتر بر اساس نام/کد کالا
- منوی کشویی → فیلتر بر اساس دسته‌بندی
- کلیک ستون → مرتب‌سازی بر اساس قیمت یا تاریخ ایجاد
- صفحه‌بندی → رد کردن و گرفتن رکوردها

مواجه می‌شویم **اگر برای هر ترکیب ممکن، APIهای جداگانه ایجاد کنیم، در نهایت با تعداد زیادی Endpoint** . OData این مشکل را با اجازه دادن به کلاینت برای ارسال کوئری در URL حل می‌کند، مانند:

- ?$filter=IsActive eq true
- ?$orderby=CreatedOn desc
- ?$top=25&$skip=50

##### **چرا IQueryable مورد نیاز است؟**

OData به این صورت کار می‌کند:

1. مخزن یک **طرح پرس‌وجو** (و نه داده‌های واقعی) را برمی‌گرداند؛ از اجرای با تأخیر استفاده می‌کند.
2. OData آدرس اینترنتی (URL) را می‌خواند و شرایط اضافی را به طرح پرس‌وجو اضافه می‌کند.
3. EF Core طرح پرس و جوی نهایی را به **یک پرس و جوی SQL واحد** تبدیل کرده و آن را در پایگاه داده اجرا می‌کند.

آن طرح پرس‌وجو دقیقاً همان چیزی است که IQueryable\<T> نشان می‌دهد.

##### **اگر به جای آن List\<T> را برگردانیم چه می‌شود؟**

اگر یک List\<Product> (که قبلاً بارگذاری شده است) برگردانیم، آنگاه:

- OData هنوز می‌تواند فیلتر/مرتب‌سازی/صفحه‌بندی کند،
- اما این کار را **پس از بارگذاری همه ردیف‌ها در حافظه** انجام خواهد داد .

یعنی:

- حجم عظیمی از پایگاه داده خوانده می‌شود
- استفاده بیشتر از رم
- پاسخ آهسته
- برای جداول بزرگ مقیاس‌پذیر نیست

برای OData، **همیشه یک** **IQueryable از مخزن** برگردانید .

##### **چرا متد Repository نباید از Include() استفاده کند؟**

منظور از Include این است که وقتی موجودیت اصلی در یک کوئری واحد از طریق JOIN بارگذاری می‌شود، موجودیت‌های مرتبط را مشتاقانه بارگذاری می‌کند. برای مثال، هر زمان که کسی محصولی را درخواست می‌کند، تمام جداول مرتبط (تصاویر، نظرات، تخفیف‌ها و غیره) را نیز دریافت می‌کند. اما اکثر صفحات نمایش به همه چیز نیاز ندارند. اگر همیشه include کنیم:

- تصاویر محصول
- نقد و بررسی‌ها
- تخفیف‌ها

سپس:

- SQL سنگین می‌شود (JOIN های بزرگ)
- صفحه بندی کند می شود
- حجم بار شبکه زیاد می‌شود
- عملکرد پایین

بنابراین، مخزن باید یک **پرس‌وجوی Clean Base با IQueryable** برگرداند و لایه‌های بالاتر تصمیم بگیرند که چه داده‌های اضافی مورد نیاز است.

##### **پیاده‌سازی در مخزن زیرساخت**

را باز کنید **فایل کلاس ProductService.Infrastructure/Repositories/ProductRepository.cs** و سپس پیاده‌سازی متد زیر را اضافه کنید.

```csharp
public IQueryable<Product> Query()
{
    // IMPORTANT:
    // Return a base IQueryable without Include().
    return _dbContext.Products.AsNoTracking();
}
```

##### **توضیحات کد:**

به جای بازگرداندن داده‌های آماده، مخزن یک IQueryable\<Product> را در معرض نمایش قرار می‌دهد تا OData بتواند **قبل از** اجرای کوئری پایگاه داده، به صورت پویا فیلتر کردن، مرتب‌سازی، صفحه‌بندی و انتخاب را اضافه کند. این کار باعث می‌شود پایگاه داده کارآمد باشد و از بارگذاری داده‌های غیرضروری در حافظه جلوگیری شود.

- IQueryable نشان دهنده تعریف پرس و جو است، نه داده ای که برمی گرداند.
- OData پرس‌وجوی خود را بر اساس این پرس‌وجوی پایه تشکیل می‌دهد.
- SQL فقط در مرحله اجرای نهایی تولید می‌شود.

##### **چرا در پیاده‌سازی از AsNoTracking() و No Include() استفاده شده است؟**

مخزن با استفاده از AsNoTracking() یک کوئری پایه تمیز برمی‌گرداند تا دسترسی فقط خواندنی را بهینه کند و از Include() برای جلوگیری از اتصالات سنگین و واکشی بیش از حد اجتناب می‌کند. این طراحی، مخزن را عمومی نگه می‌دارد و به لایه‌های بالاتر اجازه می‌دهد تا تصمیم بگیرند که چه شکل داده‌ای مورد نیاز است.

- AsNoTracking() عملکرد خواندن را بهبود می‌بخشد
- عدم استفاده از Include() به معنی عدم وجود joinهای غیرضروری است.
- مخزن همچنان بر دسترسی به داده‌ها متمرکز است، نه نیازهای رابط کاربری

#### **مرحله ۳: بهبود ProductDTO با ویژگی‌های ناوبری**

در APIهای مبتنی بر OData، DTO نقش حیاتی ایفا می‌کند زیرا **شکل دقیق داده‌هایی را که API ارائه می‌دهد** به DTO متکی است . ، نه تنها موجودیت اصلی، بلکه داده‌های مرتبط با آن را نیز تعریف می‌کند. OData برای تعیین **اینکه کدام ویژگی‌ها و روابط قابل پرس‌وجو یا قابل بسط هستند،** با استفاده از گزینه‌هایی مانند $select و $expand،

لطفاً **ProductService.Application/DTOs/ProductDTO** را به شرح زیر به‌روزرسانی کنید. افزودن ویژگی‌های ناوبری به ProductDTO مشخص می‌کند که کدام داده‌های مرتبط را کلاینت‌های OData می‌توانند جستجو یا گسترش دهند، در حالی که کنترل بر عملکرد و قراردادهای API حفظ می‌شود. در اینجا، ویژگی ناوبری Images را اضافه کرده‌ایم.

```csharp
namespace ProductService.Application.DTOs
{
    public class ProductDTO
    {
        public Guid Id { get; set; }
        public string Name { get; set; } = null!;
        public string SKU { get; set; } = null!;
        public string? Description { get; set; }
        public decimal Price { get; set; }
        public int StockQuantity { get; set; }
        public bool IsActive { get; set; }
        public Guid CategoryId { get; set; }
        public DateTime CreatedOn { get; set; }
        public DateTime? ModifiedOn { get; set; }
        public decimal DiscountedPrice { get; set; }
        public string? PrimaryImageUrl { get; set; }
        public string? PrimaryImageAltText { get; set; }
        public decimal AverageRating { get; set; }
        public int TotalReviews { get; set; }
        public ICollection<ProductImageDTO> Images { get; set; } = new List<ProductImageDTO>();
    }
}
```

##### **توضیحات کد:**

با افزودن ویژگی ناوبری تصاویر به ProductDTO، ما به صراحت به OData می‌گوییم که تصاویر محصول یک **رابطه معتبر** هستند که کلاینت‌ها می‌توانند در صورت نیاز درخواست کنند. این امر سناریوهایی مانند شبکه‌های مدیریتی، صفحات کاتالوگ یا صفحات جزئیات محصول را قادر می‌سازد تا تصاویر مرتبط را در همان درخواست بدون افشای موجودیت‌های دامنه داخلی دریافت کنند.

- DTOها **قرارداد عمومی** API را تعریف می‌کنند، نه ساختار پایگاه داده را.
- ویژگی‌های ناوبری، مواردی را که می‌توانند در OData با $expand-ed نمایش داده شوند، کنترل می‌کنند.
- فقط داده‌های مرتبط تأیید شده (مانند تصاویر) در معرض دید مشتریان قرار می‌گیرد.

##### **چرا ویژگی‌های ناوبری (Navigation Properties) به DTO تعلق دارند؟**

اضافه کردن ویژگی‌های ناوبری به DTO به **این معنی نیست** که داده‌ها همیشه بارگذاری می‌شوند. این کار فقط باعث می‌شود که رابطه **بر اساس تقاضا قابل پرس‌وجو باشد** و به سرور اجازه می‌دهد تا کنترل عملکرد را حفظ کند. بارگذاری واقعی داده‌ها همچنان به نحوه‌ی نمایش پرس‌وجو و اینکه آیا کلاینت صریحاً آن را درخواست کرده است یا خیر، بستگی دارد.

- روابط با خیال راحت در معرض دید قرار می‌گیرند، نه با اشتیاق بارگذاری می‌شوند
- مشتریان فقط در صورت نیاز، داده‌های مرتبط را درخواست می‌کنند
- مدل‌های دامنه را پنهان و پاسخ‌های API را سازگار نگه می‌دارد

#### **مرحله 4: ایجاد یک لایه پرس و جوی مختص OData**

قبل از این مرحله، مخزن ما فقط مسئول برگرداندن **برمی‌گرداند** کوئری پایه است که داده‌های خام محصول را از پایگاه داده به صورت   **IQueryable\<Product>** . حال سوال این است: **کجا باید آن داده‌های خام را به چیزی که رابط کاربری واقعاً به آن نیاز دارد تبدیل کنیم؟**

جواب **این نیست** :

- کنترل کننده
- مخزن
- سرویس تجاری موجود (برای ایجاد / به‌روزرسانی / حذف استفاده می‌شود)

در عوض، ما یک **لایه پرس و جوی جداگانه مختص OData** ایجاد می‌کنیم .

##### **این لایه کوئری OData واقعاً چه کاری انجام می‌دهد؟**

این لایه را به عنوان یک **مترجم** در نظر بگیرید :

- ورودی: **IQueryable\<Product>** (موجودیت‌های خام پایگاه داده)
- خروجی: **IQueryable\<ProductDTO>** (قرارداد API تمیز)

هنگام ترجمه، این:

- تخفیف‌ها را محاسبه می‌کند
- محاسبه رتبه‌بندی‌ها
- تصویر اصلی را انتخاب می‌کند
- مجموعه‌های فرزند اشکال (تصاویر)
- از بارگیری داده‌های غیرضروری جلوگیری می‌کند

همه اینها **قبل از اجرای SQL** اتفاق می‌افتد .

##### **ProductQueryExtensions.cs**

ابتدا، پوشه‌ای به نام **OData** در دایرکتوری ریشه‌ی **ProductService.Application** Layer Project ایجاد کنید. سپس، یک فایل کلاس به نام **ProductQueryExtensions.cs** را در **پوشه‌ی OData** اضافه کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
using ProductService.Application.DTOs;
using ProductService.Domain.Entities;

namespace ProductService.Application.OData
{
    public static class ProductQueryExtensions
    {
        public static IQueryable<ProductDTO> ProjectToProductDtoForOData(this IQueryable<Product> query)
        {
            // We capture the current UTC time once so EF Core treats it like a parameter value
            var now = DateTime.UtcNow;

            // IMPORTANT:
            // We do NOT use Include() here.
            // Instead, we shape a DTO using SQL-friendly subqueries.
            //
            // Benefits:
            // - Only fetches the data we need (projection), not entire entity graphs.
            // - Avoids huge JOINs and duplicate rows caused by multiple Includes.
            // - Keeps paging/filtering/sorting efficient (very important for OData grids).
            // - Produces a clean DTO that OData can apply query options against.
            return query
                .Select(p => new
                {
                    // Keep the root product for basic scalar fields.
                    Product = p,

                    // PRIMARY IMAGE:
                    // Fetch only the primary image (thumbnail) for grid/listing UI.
                    // This uses a subquery that EF translates into SQL efficiently.
                    PrimaryImage = p.ProductImages
                        .Where(pi => pi.IsPrimary)
                        .OrderByDescending(pi => pi.CreatedOn) // in case multiple primaries exist, pick latest
                        .Select(pi => new { pi.ImageUrl, pi.AltText })
                        .FirstOrDefault(),

                    // ACTIVE DISCOUNT:
                    // Find the most recent active discount within the time window (StartDate..EndDate).
                    // We project only the fields required to compute DiscountedPrice.
                    ActiveDiscount = p.Discounts
                        .Where(d => d.IsActive && d.StartDate <= now && d.EndDate >= now)
                        .OrderByDescending(d => d.CreatedOn)
                        .Select(d => new { d.DiscountPercentage, d.DiscountAmount })
                        .FirstOrDefault(),

                    // REVIEW SUMMARY:
                    // We compute count and average as scalars so the DB does the heavy lifting.
                    // This avoids loading all reviews into memory.
                    TotalReviews = p.Reviews.Count(),

                    AvgRating = p.Reviews.Any()
                        ? p.Reviews.Average(r => (decimal)r.Rating)
                        : 0m,

                    // IMAGE GALLERY (navigation-style):
                    // This prepares a child collection for UI pages that need an image gallery.
                    // NOTE: If you plan to use real OData $expand on entities, this part may be optional.
                    // Here, we intentionally project to DTOs so the response can include images.
                    Images = p.ProductImages
                        .OrderByDescending(pi => pi.IsPrimary)     // primary image first
                        .ThenByDescending(pi => pi.CreatedOn)      // newest first within each group
                        .Select(pi => new ProductImageDTO
                        {
                            Id = pi.Id,
                            ProductId = pi.ProductId,
                            ImageUrl = pi.ImageUrl,
                            AltText = pi.AltText,
                            IsPrimary = pi.IsPrimary,
                            CreatedOn = pi.CreatedOn
                        })
                        .ToList()
                })
                .Select(x => new ProductDTO
                {
                    // Basic product fields (scalars).
                    Id = x.Product.Id,
                    Name = x.Product.Name,
                    SKU = x.Product.SKU,
                    Description = x.Product.Description,
                    Price = x.Product.Price,
                    StockQuantity = x.Product.StockQuantity,
                    IsActive = x.Product.IsActive,
                    CategoryId = x.Product.CategoryId,
                    CreatedOn = x.Product.CreatedOn,
                    ModifiedOn = x.Product.ModifiedOn,

                    // Flattened thumbnail fields for list/grid views.
                    PrimaryImageUrl = x.PrimaryImage != null ? x.PrimaryImage.ImageUrl : null,
                    PrimaryImageAltText = x.PrimaryImage != null ? x.PrimaryImage.AltText : null,

                    // Review summary fields for UI badges and sorting.
                    TotalReviews = x.TotalReviews,

                    // Round rating for a stable UI display.
                    // (If a provider ever complains about translating Math.Round, we can round post-query.)
                    AverageRating = Math.Round(x.AvgRating, 2),

                    // DISCOUNTED PRICE:
                    // Compute effective price based on the active discount.
                    // - Percentage discount takes precedence when provided and > 0
                    // - Otherwise, amount discount applies when provided and > 0
                    // - Final protection ensures price never goes below 0
                    DiscountedPrice =
                        x.ActiveDiscount == null
                            ? x.Product.Price
                            : (x.ActiveDiscount.DiscountPercentage.HasValue && x.ActiveDiscount.DiscountPercentage.Value > 0)
                                ? Math.Round(
                                    (x.Product.Price - (x.Product.Price * x.ActiveDiscount.DiscountPercentage.Value / 100m)) < 0
                                        ? 0m
                                        : (x.Product.Price - (x.Product.Price * x.ActiveDiscount.DiscountPercentage.Value / 100m)),
                                    2)
                                : (x.ActiveDiscount.DiscountAmount.HasValue && x.ActiveDiscount.DiscountAmount.Value > 0)
                                    ? Math.Round(
                                        (x.Product.Price - x.ActiveDiscount.DiscountAmount.Value) < 0
                                            ? 0m
                                            : (x.Product.Price - x.ActiveDiscount.DiscountAmount.Value),
                                        2)
                                    : x.Product.Price,

                    // Attach the image collection to support gallery views in the same payload.
                    Images = x.Images
                });
        }
    }
}
```

##### **چرا به جای Include() از Projection استفاده می‌کنیم؟**

- **بارگذاری داده‌ها با استفاده از تابع ()Include**
- **انتخاب() داده های شکل**

اگر از Include() استفاده کنیم:

- SQL بزرگ و کند می‌شود
- صفحه بندی می تواند خراب شود

اگر از Select() استفاده کنیم:

- فقط ستون‌های مورد نیاز واکشی می‌شوند
- SQL کارآمد باقی می‌ماند
- محاسبات در پایگاه داده اتفاق می‌افتد
- صفحه‌بندی و فیلتر کردن همچنان سریع هستند

به همین دلیل است که این لایه **هرگز از Include() استفاده نمی‌کند** .

##### **ایجاد پیاده‌سازی ProductODataQueryService**

این سرویس یک کوئری پایه تمیز از مخزن می‌گیرد و **آن را با استفاده از projection به ProductDTO تبدیل می‌کند** و تضمین می‌کند که فقط فیلدهای مجاز نمایش داده می‌شوند. این سرویس داده‌ها را آماده می‌کند تا OData بتواند با خیال راحت گزینه‌های کوئری را بدون بارگذاری داده‌های غیرضروری اعمال کند.

- تصویرسازی از واکشی بیش از حد و اتصال‌های سنگین جلوگیری می‌کند
- همین منطق برای کوئری‌های لیست و تک آیتمی نیز استفاده می‌شود.

یک فایل کلاس با نام **ProductODataQueryService.cs** در **پوشه ProductService.Application/OData** ایجاد کنید و سپس کد زیر را کپی و در آن قرار دهید.

```csharp
using ProductService.Application.DTOs;
using ProductService.Domain.Repositories;

namespace ProductService.Application.OData
{
    public class ProductODataQueryService : IProductODataQueryService
    {
        private readonly IProductRepository _productRepository;

        public ProductODataQueryService(IProductRepository productRepository)
        {
            _productRepository = productRepository;
        }

        public IQueryable<ProductDTO> Query()
        {
            // Start with a simple base query from the repository (no Include).
            // We return IQueryable so the OData middleware can append query options
            // and translate the final composed query into SQL.
            return _productRepository
                .Query()
                // Project entities into a lightweight DTO using SQL-friendly subqueries.
                // This prevents over-fetching and avoids loading large navigation graphs.
                .ProjectToProductDtoForOData();
        }

        public IQueryable<ProductDTO> QueryById(Guid id)
        {
            // Key-based query for Product details.
            return _productRepository
                .Query()
                // Apply the key predicate first so the database filters early.
                .Where(p => p.Id == id)
                // Reuse the same projection to ensure consistent output shape.
                .ProjectToProductDtoForOData();
        }
    }
}
```

#### **مرحله 6: ساخت EDM (مدل داده موجودیت)**

در یک ASP.NET Core Web API معمولی، مسیریابی بسیار ساده است:

- URL **نام کنترلر،** را تعیین می‌کند.
- متد **اکشن** تصمیم می‌گیرد که چه داده‌هایی بازگردانده شوند.

اما **OData مانند یک API معمولی کار نمی‌کند** . در OData، این چارچوب **ابتدا به مسیرهای کنترلر نگاه نمی‌کند** نگاه می‌کند **. در عوض، به چیزی به نام EDM (مدل داده موجودیت)** .

##### **EDM به زبان ساده چیست؟**

می‌توانید **EDM را به عنوان یک طرح یا نقشه** در نظر بگیرید که به OData می‌گوید:

- چه داده‌هایی وجود دارد؟
- چه چیزهایی مجاز به استعلام هستند؟
- URL ها چگونه باید رفتار کنند؟

##### **چرا OData به EDM نیاز دارد؟**

برخلاف API های سنتی:

- آدرس‌های اینترنتی OData پویا هستند **.**
- کلاینت‌ها می‌توانند فیلتر کردن، مرتب‌سازی، صفحه‌بندی و انتخاب را خودشان انتخاب کنند.
- آدرس‌هایی مانند **$filter=Price gt 500** باید **به صورت خودکار اعتبارسنجی شوند.**

برای انجام ایمن این کار، OData باید **ساختار داده و پرس‌وجوهایی را که از آنها پشتیبانی می‌کند، از قبل بداند** تعریف می‌شود **. این ساختار با استفاده از EDM** .

##### **EDM چه چیزی را تعریف می‌کند؟**

EDM به وضوح به OData می‌گوید:

- کدام موجودیت‌ها در معرض خطر هستند (برای مثال: محصولات)؟
- کلید اصلی هر موجودیت چیست؟
- چه ویژگی‌هایی روی موجودیت وجود دارد؟
- چه روابطی (ویژگی‌های ناوبری) وجود دارد؟
- چه چیزی می‌تواند مورد پرسش، فیلتر، مرتب‌سازی یا بسط قرار گیرد؟

ابتدا، پوشه‌ای به نام **OData** در دایرکتوری ریشه **پروژه لایه ProductService.API** ایجاد کنید . سپس، یک فایل کلاس به نام **ProductEdmModelBuilder.cs** را در **پوشه OData** اضافه کنید و کد زیر را کپی و جایگذاری کنید.

```csharp
using Microsoft.OData.Edm;
using Microsoft.OData.ModelBuilder;
using ProductService.Application.DTOs;

namespace ProductService.API.OData
{
    public static class ProductEdmModelBuilder
    {
        public static IEdmModel GetEdmModel()
        {
            // Build the OData EDM (Entity Data Model).
            // This model is the "schema contract" for OData:
            // - /odata/$metadata generation
            // - which entity sets are exposed (e.g., /odata/Products)
            // - how OData understands keys, properties, and queryability
            var builder = new ODataConventionModelBuilder();

            // Register an EntitySet named "Products".
            // This is the collection endpoint clients will query:
            // GET /odata/Products?$filter=...&$orderby=...&$top=...&$skip=...
            builder.EntitySet<ProductDTO>("Products");

            // Explicitly define the primary key for ProductDTO.
            // OData needs a key to support:
            // - single-entity access: /odata/Products(<key>)
            // - stable identity in responses
            // - correct EDM metadata and routing behavior
            builder.EntityType<ProductDTO>().HasKey(x => x.Id);

            // Finalize and return the EDM model that ASP.NET Core OData uses at startup.
            return builder.GetEdmModel();
        }
    }
}
```

#### **مرحله 8: ایجاد یک کنترلر OData اختصاصی برای محیط عملیاتی**

این کنترلر به طور خاص برای **کوئری‌های فقط خواندنی و مبتنی بر رابط کاربری** مانند شبکه‌های مدیریتی و فهرست‌های کاتالوگ طراحی شده است. به جای فیلترهای کدنویسی شده یا چندین نقطه پایانی، دستورالعمل‌های کوئری انعطاف‌پذیر را مستقیماً از URL می‌پذیرد و آنها را با خیال راحت روی سرور اعمال می‌کند.

- ODataQueryOptions\<T> را از URL درخواستی می‌پذیرد.
- پیچیدگی پرس‌وجو را برای محافظت از پایگاه داده اعتبارسنجی می‌کند
- درخواست‌های نادرست یا توهین‌آمیز را زود رد می‌کند

لطفاً یک کنترلر خالی با نام **ProductsODataController** در **پوشه ProductService.API/Controllers** ایجاد کنید و سپس کد زیر را کپی و پیست کنید. کنترلر OData با خیال راحت یک کوئری از URL می‌سازد و آن را فقط در زمان پاسخ اجرا می‌کند و فیلترینگ و صفحه‌بندی کارآمد در سطح پایگاه داده را تضمین می‌کند.

```csharp
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.OData.Formatter;
using Microsoft.AspNetCore.OData.Query;
using Microsoft.AspNetCore.OData.Query.Validator;
using Microsoft.AspNetCore.OData.Routing.Controllers;
using Microsoft.OData;
using ProductService.Application.DTOs;
using ProductService.Application.OData;

namespace ProductService.API.Controllers
{
    // This is an OData Controller (read-only).
    // It is mainly used for UI screens like:
    // - Admin Product Grid
    // - Catalog listing pages
    //
    // Why OData here?
    // Because the UI can send queries in URL like:
    // $filter, $orderby, $top, $skip, $select, $count, $expand etc.
    //
    // Base route:
    // - GET /odata/Products
    // - GET /odata/Products(<guid>)
    [Route("odata/Products")]
    public class ProductsODataController : ODataController
    {
        // This service returns IQueryable<ProductDTO>.
        // IQueryable is required so OData can add filters/sorts/paging before SQL runs.
        private readonly IProductODataQueryService _queryService;

        // Logger for storing useful warnings when someone sends invalid OData queries.
        private readonly ILogger<ProductsODataController> _logger;

        public ProductsODataController(
            IProductODataQueryService queryService,
            ILogger<ProductsODataController> logger)
        {
            _queryService = queryService;
            _logger = logger;
        }

        // Real-time scenario: Admin Product Catalog Grid
        // Example URL:
        // /odata/Products?$filter=IsActive eq true&$orderby=CreatedOn desc&$top=25&$skip=0&$count=true
        //
        // What happens here?
        // 1) We read OData query options from URL (options)
        // 2) Validate them (for safety)
        // 3) Apply them to IQueryable
        // 4) EF Core converts final query to SQL and fetches data
        [HttpGet]
        public IActionResult Get(ODataQueryOptions<ProductDTO> options)
        {
            try
            {
                // Step A: Add safety limits (Guardrails)
                // Why?
                // OData is powerful. If we don’t limit it, a client can request huge data,
                // causing slow SQL queries and heavy load on the database.
                var validation = new ODataValidationSettings
                {
                    // MaxTop means client cannot ask more than 100 records using $top.
                    MaxTop = 100
                };

                // Step B: Validate the incoming OData query
                // If the query is wrong or too expensive, this throws an ODataException.
                options.Validate(validation);

                // Step C: Get base query from Application layer
                // IMPORTANT: This is still IQueryable (SQL is not executed yet).
                var baseQuery = _queryService.Query();

                // Step D: Configure how OData should build expressions
                // HandleNullPropagation = False usually generates cleaner SQL for EF Core.
                var settings = new ODataQuerySettings
                {
                    HandleNullPropagation = HandleNullPropagationOption.False
                };

                // Step E: Apply OData query options to IQueryable
                // Example:
                // - $filter becomes SQL WHERE
                // - $orderby becomes SQL ORDER BY
                // - $top/$skip becomes SQL OFFSET/FETCH
                //
                // Note: SQL is still executed later when data is actually enumerated.
                var result = options.ApplyTo(baseQuery, settings);

                // Step F: Return results
                // ASP.NET Core will execute the query when it writes the response.
                return Ok(result);
            }
            catch (ODataException ex)
            {
                // If someone sends invalid query like wrong syntax or too high $top,
                // return 400 (Bad Request) with message.
                _logger.LogWarning(ex, "Invalid OData query request.");
                return BadRequest(new { Message = "Invalid OData query.", Details = ex.Message });
            }
        }

        // Get a single product by Id (OData key lookup)
        // Correct URL format:
        // /odata/Products(<guid>)
        //
        // NOTE:
        // Do NOT add an extra slash like /odata/Products/(<guid>)
        // That is not standard OData key syntax.
        [HttpGet("({key})")]
        public IActionResult Get([FromODataUri] Guid key, ODataQueryOptions<ProductDTO> options)
        {
            try
            {
                // Safety validation for single item query
                // MaxTop=1 means client can’t request multiple items here.
                var validation = new ODataValidationSettings
                {
                    MaxTop = 1
                };

                options.Validate(validation);

                // Build query for one product
                // Still IQueryable so client can use $select (choose fields).
                var baseQuery = _queryService.QueryById(key);

                // Apply OData options (mostly $select here)
                var result = options.ApplyTo(baseQuery);

                return Ok(result);
            }
            catch (ODataException ex)
            {
                _logger.LogWarning(ex, "Invalid OData key query request.");
                return BadRequest(new { Message = "Invalid OData query.", Details = ex.Message });
            }
        }
    }
}
```

##### **ODataQueryOptions\<T> واقعاً چه کاری انجام می‌دهد؟**

ODataQueryOptions\<T> پارامترهای پرس‌وجوی OData مانند $filter، $orderby، $top، $skip، $select، $expand و $count را از URL می‌خواند و آنها را به یک فرم ساختاریافته تبدیل می‌کند. این گزینه‌ها **بلافاصله اجرا نمی‌شوند** \- آنها به یک IQueryable اعمال می‌شوند تا بعداً بتوان آنها را به SQL ترجمه کرد.

- گزینه‌های پرس‌وجو را از URL می‌خواند
- آنها را به درخت‌های بیان تبدیل می‌کند
- فقط با IQueryable کار می‌کند

##### **چه زمانی کوئری پایگاه داده اجرا می‌شود؟**

کوئری پایگاه داده **در موارد زیر اجرا نمی‌شود** :

- مخزن، IQueryable را برمی‌گرداند.
- گزینه‌های OData اعتبارسنجی می‌شوند
- تابع ()ApplyTo فراخوانی می‌شود.

پرس‌وجو **فقط زمانی اجرا می‌شود که نتیجه شمارش شده باشد** ، که این اتفاق زمانی می‌افتد که ASP.NET Core شروع به نوشتن پاسخ می‌کند (در داخل return Ok(result)).

- ساخت پرس‌وجو کند است (اجرا با تأخیر انجام می‌شود)
- SQL در زمان سریال‌سازی پاسخ اجرا می‌شود.
- تمام فیلترها، مرتب‌سازی و صفحه‌بندی در یک پرس‌وجوی SQL اجرا می‌شوند

#### **مرحله 9: افشای OData از طریق دروازه API**

در میکروسرویس‌ها، کلاینت‌ها هرگز سرویس‌ها را مستقیماً فراخوانی نمی‌کنند. با مسیریابی OData از طریق API Gateway:

- ما یک نقطه ورود عمومی واحد را حفظ می‌کنیم
- ما قوانین امنیتی و مسیریابی منسجمی را اجرا می‌کنیم
- ما امکان مقیاس‌بندی مستقل ProductService را فراهم می‌کنیم
- ما از دور زدن تصادفی سیاست‌های دروازه جلوگیری می‌کنیم

قرار دادن مسیر OData بالای مسیر REST، تطابق صحیح درخواست را تضمین می‌کند. **فایل ApiGateway/ocelot.json** **را باز کنید ،** سپس مسیر زیر را بالای **مسیر ProductService** موجود اضافه کنید تا ابتدا تطابق داشته باشد.

```json
{
  "UpstreamPathTemplate": "/products/odata/{everything}",
  "UpstreamHttpMethod": [ "Get"],
  "DownstreamPathTemplate": "/odata/{everything}",
  "DownstreamScheme": "https",
  "UseServiceDiscovery": true,
  "ServiceName": "ProductService",
  "LoadBalancerOptions": {
    "Type": "RoundRobin"
  }
}
```

##### **کنسول را در حالت توسعه اجرا کنید**

لطفا دستور زیر را در Command Prompt اجرا کنید.

**نماینده کنسول -dev -client=0.0.0.0 -ui -node=consul-dev**

**توجه:** هنگام کار با میکروسرویس‌های خود، این پنجره فرمان را **باز** نگه دارید . اگر آن را ببندید، Consul متوقف می‌شود و سرویس‌ها نمی‌توانند ثبت یا شناسایی شوند.

##### **رابط کاربری کنسول را باز کنید**

پس از اجرای کنسول، می‌توانیم همه چیز را از مرورگر رصد کنیم. مرورگر خود را باز کنید و به آدرس زیر بروید: **http://localhost:8500**

##### **اجرای میکروسرویس‌ها**

لطفاً تمام پروژه‌های میکروسرویس، به‌ویژه API gateway و میکروسرویس محصول را اجرا کنید.

##### **نحوه تست OData از طریق Gateway**

ما:

- پایه دروازه: https://localhost:7204
- پیشوند OData بالادست: /products/odata

##### **متادیتای تست (اولین و مهمترین)**

**دریافت** https://localhost:7204/products/odata/$metadata

اگر این کار کند، مسیریابی درست است.

##### **سناریو ۱: شبکه مدیریت – صفحه‌بندی + تعداد کل**

**صفحه اول**

دریافت https://localhost:7204/products/odata/Products?$count=true&$top=5&$skip=0

**صفحه بعد**

دریافت https://localhost:7204/products/odata/Products?$count=true&$top=5&$skip=5

##### **سناریو ۲: شبکه مدیریتی - فقط ستون‌های نمایش داده شده در رابط کاربری را انتخاب کنید (عملکرد)**

دریافت https://localhost:7204/products/odata/Products?$select=Id,Name,SKU,Price,StockQuantity,IsActive&$top=25

##### **سناریو ۳: فقط محصولات فعال (فیلتر کاتالوگ)**

دریافت https://localhost:7204/products/odata/Products?$filter=IsActive eq true

##### **سناریو ۴: نمای دسته‌بندی‌شده (صفحه دسته‌بندی)**

دریافت https://localhost:7204/products/odata/Products?$filter=CategoryId eq D7F8E3C4-6A7B-4A12-9C9F-2B3456789ABC and IsActive eq true&$orderby=CreatedOn desc&$top=20

##### **سناریو ۵: محصولات موجود در انبار (از نمایش محصولات ناموجود خودداری کنید)**

دریافت https://localhost:7204/products/odata/Products?$filter=StockQuantity gt 0 and IsActive eq true&$orderby=StockQuantity desc&$top=50

##### **سناریوی ۶: اسلایدر محدوده قیمت (۵۰۰ تا ۵۰۰۰ روپیه)**

دریافت https://localhost:7204/products/odata/Products?$filter=Price ge 500 and Price le 5000&$orderby=Price asc&$top=50

##### **سناریو ۷: ترکیب «پاور کوئری» (وضعیت واقعی شبکه مدیریت)**

دریافت https://localhost:7204/products/odata/Products?$filter=IsActive eq true and StockQuantity gt 0&$orderby=CreatedOn desc&$select=Id,Name,SKU,Price,StockQuantity,AverageRating,DiscountedPrice&$count=true&$top=25&$skip=0

##### **سناریو ۸: دریافت محصولات با تصاویر (باز کردن)**

دریافت https://localhost:7204/products/odata/Products?$top=10&$expand=Images

##### **سناریو ۹: تصاویر را باز کنید اما فقط فیلدهای تصویر مورد نیاز را بیاورید (select تو در تو)**

دریافت https://localhost:7204/products/odata/Products?$top=10&$select=Id,Name,Price&$expand=Images($select=Id,ImageUrl,IsPrimary)

##### **سناریو ۱۰: تصاویر را فقط برای یک محصول (صفحه جزئیات محصول) گسترش دهید**

دریافت https://localhost:7204/products/odata/Products/(C968B396-8C5B-47F5-8D2E-4C9A6DD7F37D)?$expand=Images

##### **نتیجه‌گیری: چرا OData اهمیت دارد؟**

OData به یک نقطه پایانی API اجازه می‌دهد تا بسیاری از نیازهای رابط کاربری - مانند شبکه‌های مدیریتی، فهرست کاتالوگ‌ها و گزارش‌ها - را بدون ایجاد چندین نقطه پایانی برای هر فیلتر یا صفحه، برآورده کند. این امر API را ساده نگه می‌دارد و در عین حال به frontend انعطاف‌پذیری کامل می‌دهد تا دقیقاً داده‌های مورد نیاز خود را درخواست کند.

وقتی OData به درستی با اعتبارسنجی، DTOها، پرس‌وجوهای کارآمد پایگاه داده و کنترل API Gateway استفاده شود، به جای یک ریسک عملکردی، به یک راه‌حل ایمن و مقیاس‌پذیر تبدیل می‌شود.

- یک نقطه پایانی از سناریوهای رابط کاربری زیادی پشتیبانی می‌کند
- اعتبارسنجی از پایگاه داده محافظت می‌کند
- DTOها کنترل می‌کنند که چه داده‌هایی در معرض دید قرار گیرند.
- ادغام درگاه، دسترسی را ایمن نگه می‌دارد

OData پیچیدگی API را کاهش می‌دهد و در عین حال دسترسی به داده‌ها را برای برنامه‌های مدرن مبتنی بر رابط کاربری، انعطاف‌پذیر، کارآمد و کنترل‌شده می‌کند.
